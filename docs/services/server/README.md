> 核心 portal/admin/console 与论坛接口的应用组装、资源生命周期和真实 GitHub 适配；一个 Fastify 进程。

状态：`current` · 更新：2026-10-31 · 源码：`app/server/` · 镜像：`yzgc-<environment>/server:<sha12>`

## 契约

- **入口职责**：`buildApp` 注册真实应用但不监听；只有 `index.ts` 读取环境并监听。测试通过 `inject` 注册真实路由，只把 `DB_PATH` 指向内存库。
- **依赖方向**：`config → lib → middleware → routes`。`middleware` 不导入 `routes`；`lib` 不反向依赖 `middleware`；身份/持久化适配器只接收普通参数，不接受 Fastify 请求/响应对象。
- **运行时装**：`DB_PATH` 指向 SQLite（WAL，better-sqlite3，`secure_delete` 打开，#128）；`sessions`、`invite_links`、`invite_attempts`、`invitations`、`feedback`、`applications`、`application_reviews`、`application_limits`、`departments`、`role_assignments`、`titles`、`console_seeds`、`competitions`、`competition_signup_settings`、`competition_signups`、`competition_teams`、`competition_team_members`、`competition_score_events`、`competition_site_versions`、`competition_sites`、`competition_gitlab_sources`、`competition_score_candidates`、`competition_rules`、`competition_finals`、`competition_prizes`（#278）、`audit_logs`、`app_state`、`mail_outbox`、`users`、`identities`、`identity_audit`、`device_grants`、`invite_codes`、`email_challenges`、`oauth_clients`、`oauth_subjects`、`oauth_grants`、`oidc_payloads`、`gitlab_accounts` 与论坛的 `forum_*` 表由本服务拥有，其中 `app_state` 是键值表，现有三个键：`gitlab_settings`（GitLab 同步设置）、`apply_open`（招新总开关，#284，缺行开放）与 `security_decoy_until`（合成蜜罐截止时间，#333，缺行关闭）；#274 新权限体系另加 `perm_nodes`、`perm_groups`、`perm_group_parents`、`perm_entries`、`perm_members`、`perm_state`（节点、分组、继承、条目、成员与引擎版本号）与 `account_profiles`、`account_avatars`、`activity_events`、`limit_events`，#343 统一头像另加 `github_avatar_checks`（GitHub 头像的像素图识别结论），和旧的 `departments`/`role_assignments`/`titles`（能力授权）并存，迁移脚本见下。每张表的写入方、读取方、个人信息字段和未使用对象见 [数据模型](data-model.md)。
- **有效成员资格与站长**（GitHub #271 回归）：`identity-store.membershipOf()`、`isMember()`、对外 claims 与 GitLab 对账共用同一口径：账号必须 `active`，且直接属于 `level.member` 或 `level.alumni`，成员资格的 `expires_at` 为 NULL 或严格大于当前时刻；到期等值立即失效，不读旧 `org_state/org_role` 授权。站长只认 active 账号的当前有效直接 `title.site.owner`，继承或过期称号不算；站长称号本身不替代 OIDC 成员资格。合法 alumni 是成员，只有同时是有效站长时 `site_role=admin`，普通 alumni 不因此得到论坛写节点。
- **时间敏感的权限缓存**：缓存同时记录 revision、`evaluatedAt`、`expiresAt`，只有 revision 未变且当前时刻在 `[evaluatedAt, expiresAt)` 内才复用。上界取未来直接成员资格和已解析条目最近到期时间，allow、deny、meta 及继承条目都计入；访客也有独立的条目缓存。到期等值或时钟回退到求值时刻之前都重读；写入仍必须 `permissions.bump()`，时间失效不代替写入失效。
- **公开资料唯一来源与论坛兼容**：统一公开 DTO 为 `{username,display_name,bio,avatar_url}`（`public-profile.ts`），现有 `account_profiles` 优先，空昵称回退登录名，头像是统一头像（见下一条）。论坛 state、changes、单用户、搜索、建议、@提及与昵称占用检查按这一来源读取，历史作者无需本人重新访问论坛；批量 `findMany()` 只查已有公开字段，不为历史作者调用 `get()/ensure()` 建档。没有 canonical 行的旧作者保留既有昵称、简介，头像按统一头像取（没有资料行时论坛上传的头像算上传的头像）；无 account_id 的旧成员按论坛上传的头像、记下的 GitHub 头像（像素图不算）、按用户名挑的 NANO 默认头像取；游客和官方账号保留既有回退（论坛上传的头像，没有就是色块），作者 id 和正文不重写。旧论坛资料写口在已有 canonical 行时，将昵称/简介与旧 `forum_users` 字段同事务写；上传头像同事务兼容两份引用，清除头像清两边引用并各自按引用清理。所在地、网站和通知设置仍是论坛数据，不做按时间双主合并或全库迁移。
- **统一头像**（#343）：同一个人在官网、论坛、控制台、比赛（含比赛官网）、命令行、OIDC 的 `picture` 和 GitLab 上是同一张头像，全部由 `lib/avatars.ts` 按顺序取：① 账号上传的头像（`account_profiles.avatar_hash`）；② GitHub 头像，GitHub 给没设头像的人自动生成的像素图不算（420×420、出现最多的两种颜色占 97% 以上且其中一种是 #F0F0F0，`lib/github-avatars.ts` 用 sharp 判断）；③ NANO 默认头像，8 张图里按这个人在 GitLab 上的主邮箱（`canonical_email`，没有时是 GitLab 建号用的占位地址 `<GitLab 用户名>@noreply.<sector>`，`gitlab-sync.ts` 的 `gitlabAvatarIdentifier`，站内和同步共用）去空白转小写后 SHA-256 的第一位十六进制模 8 挑，和 GitLab 前置（`deploy/remote/edge-gitlab.py` 生成的 `/gitlab/nano-avatar/` 映射）挑的同一张。网站请求不下载 GitHub 图片：识别结论按 GitHub 头像地址记在 `github_avatar_checks`，由后台任务（`buildApp({ githubAvatarCheck: true })`，只有 `index.ts` 打开）启动时和之后每 10 分钟查还没结论或结论超过 7 天的地址，上传了头像的人不查；真头像同时按账号头像规格（512 WebP）在 `account_avatars` 存一份，接口给这份同源副本（`/api/identity/avatar/<hash>.webp`），比赛官网的 sandbox CSP 只放行同源图片也能显示；还没结论时先给 GitHub 地址。NANO 图随 server 镜像发布（`deploy/gitlab/ui/nano-avatars/20261025/`，和 GitLab 前置是同一份文件），由 `GET /api/identity/default-avatar/:version/:file` 长期缓存下发，不依赖 GitLab 或 CDN。`GET`/`PATCH /api/identity/profile` 与 `PUT /api/identity/avatar` 的 `avatar_url` 仍只表示上传的头像（资料卡要知道有没有上传过）。控制台的首字母头像只在没有地址时出现，统一头像总有地址。
- **单一 origin**：每个环境只有一个对外地址 `PUBLIC_ORIGIN`（正式 `https://yangtzeu.work`、预发布 `https://prev.yangtzeu.work`）。OAuth `redirect_uri` 是 `<PUBLIC_ORIGIN>/auth/callback`，登录后默认回 `<PUBLIC_ORIGIN>/console`，邀请链接是 `<PUBLIC_ORIGIN>/join/<token>`；`return_to` 与写请求的 `Origin` 只接受这一个 origin。
- **SPA 入口按路径选择**：服务端直接托管前端产物时，`resolveSiteEntry` 把管理端路径（`ADMIN_SPA_PATHS`：`/admin`、`/admin/…`、`/console`、`/console/…`、`/signin`、`/device`、`/account`、`/authorize`、`/bind-email`、`/complete-profile`）交给管理端入口（`ADMIN_SPA_ENTRY` = `sites/console/index.html`，即 `app/console` 的产物），其余交给 portal 入口，与 Host 无关；两者各只在 `app.ts` 定义一处，web 容器 nginx 的 location 与之一致。管理端换成别的前端产物时只改入口常量。
- **身份**：全站只有这一个登录，官网、论坛、控制台共用它签发的 `sid`（服务器会话，host-only）；会话有效期 7 天，`expires_at <= now` 时请求立即按未登录处理，主动清理采用相同到期边界；过期行由服务主动清理（启动时一次、之后每小时一次，#128）；不签发、不桥接旧 `forum_sid`。GitHub OAuth 保留签名 state、十分钟有效期和允许列表回跳。`/auth/callback` 换到 token、取到 `/user` 之后不再查 GitHub 组织（#274）：按 GitHub 数字 id 找到或建立极客班账号，第一次登录不填邀请码建成注册用户（`level.registered`），填了有效邀请码建成成员（`level.member`）；建号受注册限额约束（同一个 IP 每个北京日 5 个、同一个设备 3 个，`lib/register-limits.ts`）。失败一律 302 到统一登录页 `<PUBLIC_ORIGIN>/signin?signin=<原因>&return_to=<原来要回的本站路径>`，原因是 `account_disabled`、`invite_invalid`、`registration_limited`、`failed`、`cancelled` 等（`lib/safe-return.ts` 的 `SigninOutcome` 与 `signinFailureUrl`；原路径里残留的 `signin` 参数会去掉，成功仍回到 `return_to`）。每个会话绑定一个极客班账号（#262，`sessions.openid`，接口里叫 `account_id`）：建号或找到账号、兑换邀请码、认领称号与论坛用户、插入会话、删掉请求带来的旧 `sid` 在一个事务里（`lib/identity-store.ts`），失败整体回滚、按 `failed` 回登录页；账号已停用时不建会话、回 `signin=account_disabled`。成功记 `auth.signin`（新号记 `auth.register`），被拒记 `auth.signin_denied`。读会话时没有账号或账号不是 `active` 的按未登录处理并删掉。启动时回填旧会话、称号和论坛用户，见 [数据模型](data-model.md)。换 token 与取 `/user` 的请求 15 秒超时。会话里存的 GitHub 令牌被 GitHub 以 401 拒绝（用户撤销了授权，或同一用户的令牌超过 10 个、最久没用的被收回）时，这个会话就结束：`middleware/http-policy.ts` 的错误处理对带会话的请求删掉会话、清 `sid`，回 401 `session_expired`，审计 `auth.session_rejected`；`/auth/me` 遇到同样情况回 `{ signed_in: false, session_expired: true }`（`middleware/require-auth.ts` 的 `endRejectedSession`，#164）。登录之后的业务路由不再用会话令牌调 GitHub，这条只作为通用处理留着。规则见 [SECURITY](../../architecture/SECURITY.md)「登录门槛」，状态码见 [API](../../architecture/API.md)。

- **限流**：`@fastify/rate-limit` 以 `global: false` 注册，只管写了 `config.rateLimit` 的路由，计数落在 `rate_limit_counters`（`lib/rate-store.ts`），重启后同一窗口内的次数不清零（#333）（官网投递、意见箱、邀请链接、控制台导出 CSV 与指派、比赛报名写操作与名单导出（#239）、论坛按 IP 计的浏览类接口、设备授权 5 个接口、邮箱登录与账号页的写接口、注册邀请码的写接口（#262）、对外授权的协议端点与交互接口、GitLab 单个账号的重试（#270）、比赛官网上传与发布、待确认贡献的确认、驳回与收集、计分规则、定榜、兑奖码查找与核销（#278））；比赛的公开接口另按 IP 记在 `limit_events`（`public.competition.per_minute`，每分钟 120 次），输错的兑奖码按账号记（`competition.prize.lookup.fail`，每小时 20 次），超了同样回 429 `rate_limited`，带 `bucket` 与 `retry_after`；超额时都回 429 `{ error: "rate_limited", message: "操作太频繁，请稍后再试", request_id }`。`app.ts` 注册插件时把 `middleware/http-policy.ts` 的 `rateLimited()` 设成默认的 `errorResponseBuilder`，路由不另写；论坛自己数次数的限流（发帖、回复、头像）抛的也是它（#191）。插件把 `errorResponseBuilder` 的返回值当错误抛给错误处理器，错误处理器只认 `statusCode` 与 `code`，所以要返回带这两项的 Error：返回 `{ statusCode, error, message }` 这样的普通对象会被回成 `request_error`。回归测试在 `tests/server/rate-limits.test.ts`。

## 已知限制

- 没有多实例/多进程协调：SQLite 单文件 + 命名卷，同一环境只跑一个 server 容器。
- 没有迁移到 Postgres；`DB_PATH` 仍为 SQLite 文件（见 [ARCHITECTURE](../../architecture/ARCHITECTURE.md)）。
- 邀请的 GitHub 结果未知时保留待核对状态，需要人工核对后由授权维护修正，不会自动重发。
- `app/server/package.json` 仍声明旧上传与旧论坛遗留依赖：`@fastify/multipart`、`multer`、`marked`、`dompurify`、`isomorphic-dompurify` 在 `src` 中零引用。`bcryptjs` 从 #262 起在用：邮箱密码登录与账号页设密码（`routes/identity/email.ts`、`account.ts`，经 `lib/password-policy.ts`）。`sharp` 已在用：论坛头像上传（`lib/forum-avatar.ts`，#57）。唯一的上传接口是 `PUT /api/forum/me/avatar`，请求体就是图片本身，没有注册 multipart 插件。删除其余遗留依赖和死代码要另开 issue 并更新锁文件。
- 论坛的 `GET /api/forum/state` 全量下发用户、话题、帖子摘要与关注，没有分页；**不含帖子正文**（#156）：`posts[]` 只有字段加服务端截好的一行摘要 `excerpt`，正文由 `GET /api/forum/topics/:topic_id/posts` 在进话题页时按话题取，搜索由 `GET /api/forum/search` 在服务端按标题、正文、名字匹配。写接口从 #145 起只回这次改动的记录（`changes`），其中帖子这一条与 `/state` 里的同一条一样（摘要，没有正文），只有发帖、回复、编辑、删除多带 `content`。见 [API](../../architecture/API.md)「论坛」。当前论坛授权不查询 GitHub 组织角色；公开资料投影不要求历史作者再来触发刷新，但角色/称号刷新仍与资料投影是不同路径。
- 名单导出 `GET /api/console/competitions/:competition_id/roster.csv` 与投递导出一样只声明入参与查询参数，没有响应 Schema（CSV 是文本流，不是 JSON）；`scripts/check-architecture.mjs` 要求新增接口声明响应 Schema，因此这一条在宏观对齐里报缺项，补齐要在 `routes/console/contracts.ts` 给 200 加文本响应声明，属于代码改动。
- 统一登录第二、三期（#262）还没做的：账号页只能绑定邮箱，GitHub、Google 的绑定与任何解绑都没有；邮箱、Google 会话的 `sessions.access_token_encrypted` 存的是空串加密后的值（列是 NOT NULL，重建表放到以后）。Google 登录要等配了凭据和隐私说明页才会出现。
- 自动发信回归使用虚构的外部请求；真实发信记录及邮件客户端验收范围只在 [mail](mail.md)「已知限制」维护，不在本页复制一份状态。没有退信和投诉回调；同一环境只有一个 server 容器，发信循环没有多进程协调，租约过期重发可能重复。
- `app/server/scripts/` 只剩已退役的占位文件，运行即失败退出，不是任何流程的入口；邀请流程的回归由 `pnpm test` 覆盖。
