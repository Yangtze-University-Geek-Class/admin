# ADR-0001：统一入口与模块化单体

> 保留一个部署单元，通过模块合同、应用工厂和自动检查降低耦合。

状态：`accepted` · 更新：2026-09-12

## 背景

产品有三个访问端，但共享认证桥接、运行环境和部分业务存储。旧问题主要是导入边界不可验证、导入即产生副作用、业务规则分散和文档漂移，不是缺少微服务。

## 决策

保留根 `app/web`、`app/server` 两个工作区包（论坛为独立包 `app/forum`）；按 portal/forum/admin 划分路由和页面；根 README 为人类入口，AGENTS 为 Agent 导航；完整规范集中 docs。通过 `buildApp`、服务工厂和内存数据库测试消除全局资源耦合。跨模块不直接导入路由实现。

采用 TypeScript AST 检查而不是正则近似检查。增加 Vitest、组件测试和浏览器验证，不同时迁移框架大版本。Node 22 是本次项目基线，不宣称它是所有场景最优或最新。

UI 优先利用浏览器平台：原生 modal dialog 和由统一 Select 适配器封装的原生选择行为。历史的「任何位置都禁止原生 select」撤销；业务页面仍统一使用适配器。理由是键盘、移动选择和焦点行为可验证，减少自研交互状态；不是宣称无需浏览器测试或自动符合 WCAG。

## 后果

三个服务分别打包为 `yzgc/web`、`yzgc/server`、`yzgc/forum` 镜像，但同一环境仍由**一个** compose 栈交付（2026-09-23 起为同机两套栈：`/opt/yzgc/production`、`/opt/yzgc/preview`），不能单独按服务扩容或多节点调度；跨库操作没有分布式事务。共享服务中仍有历史代码可继续按职责提炼，不能把一个巨大 service locator 当成万能入口；模块只取自己需要的服务。UI 平台控件在不同系统有细微外观差异，以一致品牌和可靠交互为优先。

## 重新评估条件

独立发布、扩缩容、安全隔离或团队所有权产生真实需求时再评估独立应用（论坛已因用户明确要求而独立为另一个技术栈的包，见 [ADR-0003](0003-adopt-tuff-forum.md)）。性能问题先测量，不先换数据库/框架。正式生产应用本决策前必须完成发布验证，代码修改本身不代表已经部署。
