# Pull Request 与审查规范

> PR 是一次改动的证据档：写清解决链路、验证结果、可以直接照着做的人工验收步骤和截图录屏；审查与返工写成评论，合并后 issue 自动关闭。

状态：`current` · 更新：2026-09-25

## 目标分支

MR 只能指向 `stage`。`main` 不接受来自 `task/**`、`dev/**` 的 MR，只接受在预发布验收通过后把 `main` 快进到被验收提交的操作（见 [BRANCHING](BRANCHING.md) 与 [RELEASES](RELEASES.md)）。合并本身不部署，发版靠打 tag。合并后立刻删除来源 task 分支。

## 正文契约

一件事 = 一个 issue = 一个 `task/<issue>/<slug>` 分支 = 一个 PR（生命周期见 [TRACKING](TRACKING.md) §1）。标题遵循 [COMMITS](COMMITS.md)。正文从模板 `.github/pull_request_template.md` 开始写，**九个段落一个都不能少**；CI 的 `pr-contract` 检查（`.github/workflows/issue-lifecycle.yml` 调 `scripts/pr-contract.mjs`）逐项核对，改 PR 描述会自动重跑：

| 段落（`### 标题`） | 要求 | CI 核对 |
|---|---|---|
| 目的 | 解决什么问题、谁提的、为什么现在做；引用 issue 里的原话 | 非空 |
| 关联 | `Closes #<issue>`，与分支号一致、只关这一个；相关的写 `Refs #n`，依赖写 `Depends on #n` | issue 号一致、issue 存在且开着、不关别的 issue |
| 变更范围 | 按服务列出改了什么，再写明「不做什么」 | 非空 |
| 解决链路 | 复现 → 定位（根因与怎么确认的）→ 修复（为什么这样改、否决了什么）→ 验证（能区分修复前后的回归） | 非空 |
| 验证命令与结果 | 实际跑过的命令 + 真实输出摘要；失败、跳过、未验证的逐条列出 | 非空 |
| 验收证据 | 界面改动放改前改后截图（桌面与手机各一），动画放逐帧拼图或录屏；每项写编号、尺寸 / 设备、对应的验收点。没有界面变化写「无界面变化：<理由>」 | 至少一张图 / 视频 / 附件链接，或写明无界面变化 |
| 人工验收步骤 | 给验收人照着做的清单：打开哪个地址（写版本或 commit）→ 做什么 → **应看到**什么 | 非空 |
| 审查结论 | 按 [CODE-REVIEW](CODE-REVIEW.md) 逐项；审查人、时间、被审查 commit；最后一行 `**结论：通过**` / `**结论：有条件通过**` / `**结论：阻塞**` | 有结论行 |
| 风险与回滚 | 已知风险、没覆盖到的环境、回滚方式（revert 合并提交 / 镜像 tag） | 非空 |

截图与录屏直接拖进 GitHub 编辑框上传（仓库是私有的，附件同样只有成员可见）；本机路径（`/tmp/...`）别人看不到，不算证据。修复漏洞不把真实凭据或可利用的生产数据放入公开讨论。

## 评论与生命周期

- 审查意见、返工、人工验收结果写成评论，格式统一用 [TRACKING](TRACKING.md) §3 的追踪记录（`review` / `rework` / `accept`），不改写已发出的评论。
- 合并进 `stage` 后：`branch-hygiene` 删除 task 分支，`issue-lifecycle` 关闭 issue 并在 issue 与 PR 上各留一条「关闭」记录。工作流失败时合并的人当场手工补齐。
- 已合并的 PR 不再追加提交；验收发现的新问题开新 issue，`Refs #<原 issue>`。

## 审查要求

逐项清单、产出格式、结论写法与记录位置以 [CODE-REVIEW](CODE-REVIEW.md) 为准（本文件不重复该清单）。除此之外还要检查：

- 授权是否由服务端强制；输入是否经过运行时合同；数据库计数和状态是否原子且可重复；
- 外部请求是否有超时和结果未知处理；共享层是否反向依赖模块；测试是否注册真实代码并隔离资源；
- 文档是否把计划当事实；`app/` 新增服务是否同时补了 `docs/services/<svc>/README.md`。

UI 变更检查键盘、焦点、名称、错误与空状态、窄屏和导航。引入新依赖说明必要性，不因为教程使用某库就照搬整套框架。

## 机器人开的 PR

组织审查机器人（[TRACKING](TRACKING.md) §6）为 issue 开的修复 PR，除本文其余要求外还要满足：

- 分支是 `task/<issue>/<slug>`，推到同一个仓库（不从 fork），目标分支 `stage`；不带 tag，不强推。
- 只做没有界面变化的改动，「验收证据」写 `无界面变化：<理由>`。
- 「人工验收步骤」照样要写，给验收人照着做。
- 「审查结论」固定写：

  ```markdown
  等待人工审查：机器人不能替人下审查结论，审查人按 CODE-REVIEW 逐项审完后改写本段。
  **结论：阻塞**
  ```

  机器人从不写「通过」或「有条件通过」。审查人改写本段后才能合并。
- PR 开出后机器人不再改正文。返工推到同一分支，并发 `kind=rework` 记录说明改了什么。
- 批准与合并只由人做。

## 门禁

根 `pnpm verify` 必须通过，相关浏览器用例通过或明确标为待验收。不得删除失败断言来取得绿色结果。无密钥、真实业务数据库、依赖缓存或无关改动。文档索引和相对链接有效（`pnpm check:docs`）。

CI 文件是否被远端执行、分支保护是否生效，需仓库管理员实际配置确认；本地提供命令不等于已有远端保护。合并、部署与发布是独立授权操作，不由 Agent 默认执行。
