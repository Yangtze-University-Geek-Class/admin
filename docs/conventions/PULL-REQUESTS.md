# Pull Request 与审查规范

> 审查代码、合同、权限、数据一致性、文档与实际验证证据；每个 MR 都写清 range、验证命令与审查结论。

状态：`current` · 更新：2026-09-23

## 目标分支

MR 只能指向 `stage`。`main` 不接受来自 `task/*`、`dev-*` 的 MR，只接受把 `stage` 合入 `main` 的发布操作（见 [BRANCHING](BRANCHING.md) 与 [RELEASES](RELEASES.md)）。合并后立刻删除来源 task 分支。

## PR 内容

标题遵循 [COMMITS](COMMITS.md)。正文必须包含：

| 字段 | 要求 |
|---|---|
| 目的 | 这个 MR 解决什么问题，为什么现在做 |
| 关联 | `Closes #<issue>`；issue 编号必须与分支名一致 |
| 变更范围 | 受影响的服务/模块（`app/server`、`app/web`、`app/forum`、`deploy`、`docs` 等）与明确的非目标 |
| 实现与取舍 | 关键决策、被否决的替代方案；兼容性影响与数据迁移 |
| 验证命令与结果 | 实际跑过的命令和真实输出摘要（`pnpm verify`、`pnpm test:e2e`、`pnpm forum:verify` 等），失败与未验证项如实列出 |
| 审查结论 | 按 [CODE-REVIEW](CODE-REVIEW.md) 的清单逐项检查后的结论：`阻塞` / `有条件通过` / `通过`，附审查人与时间 |
| 风险与回滚 | 已知风险、残余不确定性、回滚方式（镜像 tag / 配置） |

修复漏洞不把真实凭据或可利用的生产数据放入公开讨论。

## 审查要求

逐项清单、产出格式、结论写法与记录位置以 [CODE-REVIEW](CODE-REVIEW.md) 为准（本文件不重复该清单）。除此之外还要检查：

- 授权是否由服务端强制；输入是否经过运行时合同；数据库计数和状态是否原子且可重复；
- 外部请求是否有超时和结果未知处理；共享层是否反向依赖模块；测试是否注册真实代码并隔离资源；
- 文档是否把计划当事实；`app/` 新增服务是否同时补了 `docs/services/<svc>/README.md`。

UI 变更检查键盘、焦点、名称、错误与空状态、窄屏和导航。引入新依赖说明必要性，不因为教程使用某库就照搬整套框架。

## 门禁

根 `pnpm verify` 必须通过，相关浏览器用例通过或明确标为待验收。不得删除失败断言来取得绿色结果。无密钥、真实业务数据库、依赖缓存或无关改动。文档索引和相对链接有效（`pnpm check:docs`）。

CI 文件是否被远端执行、分支保护是否生效，需仓库管理员实际配置确认；本地提供命令不等于已有远端保护。合并、部署与发布是独立授权操作，不由 Agent 默认执行。
