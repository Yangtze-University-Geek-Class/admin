# Issue 规范

> issue 是一件事的主档：开发前先开 issue，写清现象、复现、环境与验收条件；之后每一步进展都以追踪记录留在评论里，PR 合并即关闭。

状态：`current` · 更新：2026-09-25

## §1 开发前先开 issue

**任何 `task/<issue>/<slug>` 分支都必须先有对应 issue**（唯一例外是维护者明确声明的紧急修复，且事后 24 小时内补 issue）。先查重再开新 issue：在 issue 列表按模块、关键词、错误信息搜索（含已关闭），确认没有同一件事；重复的直接在原 issue 补一条「复现」记录。

**一件事一个 issue**：一个 issue 只描述一件可以独立验收的事。所有者一次提了几件事（例如「去掉招人字样 + 开机闪桌面 + 换壁纸」）时，能一起验收的放一个 issue，不能一起验收的拆开，互相 `Refs #n`。

生命周期、互相引用和评论格式见 [TRACKING](TRACKING.md)。要点：

| 关联 | 位置 | 要求 |
|---|---|---|
| issue → 分支 | `task/<issue>/<slug>` | 一个 issue 一条 task 分支 |
| PR → issue | PR 正文「关联」段 `Closes #<issue>` | 与分支号一致，CI 的 `pr-contract` 核对 |
| issue → PR | issue 正文「实施」段 | 回填分支名、PR 链接、合并提交 |
| 进展 | issue 评论 | 按 [TRACKING](TRACKING.md) §3 的格式，每个阶段一条 |
| 谁来做 | 负责人（assignee）、`bot:manual` 标签 | 见 §5 与 [TRACKING](TRACKING.md) §6 |

**PR 合并进 `stage` 即关闭 issue**：`issue-lifecycle` 工作流自动关闭并在两边留「关闭」记录，`branch-hygiene` 删除 task 分支。GitHub 自带的 `Closes #n` 只在合进 `main` 时生效，不能依赖它。工作流失败时，合并的人当场手工关闭并补记录。已合并的分支不再提交；后续问题开新 issue。

## §2 正文内容

标题：`<模块>：<用户可见的症状或诉求>`，模块取「端」的标签名（portal / forum / admin / server / shared / bot / deploy / docs）。

### 缺陷

| 段落 | 要求 |
|---|---|
| 现象 | 实际看到了什么：原文报错、截图（直接拖进编辑框上传）、录屏；动画问题附逐帧图 |
| 复现步骤 | 最小路径，编号，每步写操作与看到的结果；偶发的写复现概率与已知条件 |
| 期望 | 应该是什么样 |
| 影响 | 谁会遇到、多严重、有没有绕过办法；决定优先级 |
| 环境 | 见 §3 |
| 验收条件 | 怎样算修好：可观察的结果 + 要在哪些尺寸 / 设备 / 环境看 |

### 需求 / 改进

写用户场景、范围和**不做什么**、接口 / 权限 / 数据影响、验收条件。描述问题与期望，不写实现方案（方案写在 PR 的「解决链路」或 issue 的「方案」记录里）。依赖升级说明动机、官方迁移来源和回退策略，不把「最新版」当成唯一理由。

严重性按真实影响区分：阻断核心流程、数据或权限风险为 P0；主要功能受损或已排期为 P1；其余 P2。未经复现的怀疑标为待确认，不以肯定语气写已证实漏洞。

## §3 环境与设备

**必填**：

- 分支与完整 commit SHA（`main` / `stage` / `task/<issue>/<slug>`），不写已退役的分支名；
- 站点与地址（本机 `127.0.0.1:5173`、预发布 `https://prev.yangtzeu.work`、正式 `https://yangtzeu.work`）；
- 页面显示的版本：正式 `X.Y.Z`，预发布 `X.Y.Z-rc.N@<sha12>`，能对应到发布 tag 时一并写上（见 [RELEASES](RELEASES.md)）。

**按问题类型补充**（与问题无关的不写，不为凑字段填）：

| 问题类型 | 需要的设备信息 |
|---|---|
| 布局、溢出、竖屏适配 | 视口尺寸（如 390×844）、设备像素比、横竖屏 |
| 3D、动画、帧率、卡顿 | 浏览器与版本、GPU / 机型、屏幕刷新率、是否前台真实浏览器（自动化浏览器会把动画页限在约 30Hz，不能用来判断帧率） |
| 触屏、手势、输入 | 设备型号、系统版本、浏览器 |
| 登录、权限 | 身份（游客 / 成员 / 哪个称号），**不贴会话、令牌或 cookie** |
| 接口、数据 | 请求路径、状态码、`requestId`；不贴完整请求头和真实数据 |

## §4 关闭与安全

关闭前 issue 上必须能查到对应 PR 与验证结果（自动「关闭」记录已包含）；不能仅因代码存在或构建成功关闭功能缺陷。放弃、重复、被取代的 issue 先发一条「关闭」记录写明原因再关。

安全问题私下报告，不贴 Token、真实会话、完整请求头或生产数据库。

## §5 分配与机器人

组织审查机器人会按 [TRACKING](TRACKING.md) §6 的「谁来做」表处理没人认领的 issue（截至 2026-09-25 还没上线，规则先行）。开 issue 的人用负责人和标签告诉它该不该接：

| 想要 | 怎么做 |
|---|---|
| 自己或指定的人来做 | 把 issue 分给这个人；机器人不接、不追问、不关 |
| 人来做，但还没定是谁 | 打 `bot:manual` |
| 让机器人来做 | 分给机器账号，它会排在 issue 的最前 |
| 让机器人自己判断 | 什么都不做；机器人会受理，小改动可能自己修 |

- 分配 issue 需要仓库的 Triage 以上权限。没有这个权限的人，在 issue 里写明想让谁来做，由维护者分配。
- 机器人在 issue 最后一次变动后静默 5 分钟才看它：负责人和标签在开 issue 后 5 分钟内补齐。
- `bot:blocked` 表示机器人追问后在等回复。回复（评论或修改正文）后由机器人自己去掉；人也可以直接去掉。第 5 天没人回复会提醒，第 7 天机器人关闭 issue。
- 机器人可能关闭价值不高的 issue，或把说清楚了但不合本规范的 issue 改写成一个新 issue、关闭原 issue。每次关闭都会先留「关闭」记录写明原因。觉得关错了，直接重开；人重开过的 issue，机器人不再关。
