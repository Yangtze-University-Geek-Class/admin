# Issue 规范

> issue 是经 Crosery 确认事项的主档：查证、查重、确认后建单；写清现象、验收条件和确认依据，进展以追踪记录留在评论里，PR 合并即关闭。

状态：`current` · 更新：2026-10-18

## §1 Crosery 确认后建单，再开发

**建单须 Crosery 明确批准具体事项。** Agent 先查证问题，再按模块、关键词、错误信息搜索开放与已关闭的 issue；将「痛点／解决方案／最终效果与验收条件」及查重结果作为候选交给 Crosery。只有确认后，才可新建、拆分、补建、重开或建立替代 issue，并在正文保留确认依据。未确认只保留候选，不建 issue 或 task 分支，不擅自实施候选。

**任何 `task/<issue>/<slug>` 分支都必须先有对应的已确认 issue。** 「开发前先 issue」是顺序约束，不是建单授权；审查建议、巡检、紧急补单、合并后续作或外部等待也不豁免确认。紧急修复先取得 Crosery 对具体紧急事项、操作范围及建单安排的确认；若已授权先处理后补单，按该安排执行，不从“紧急”自行推导授权或补单时限。

**一件事一个 issue**：一个 issue 只描述一件可以独立验收的事。一次提出几件事时，先提出合并或拆分候选，由 Crosery 确认各项范围；确认拆分后才建单并互相 `Refs #n`。重复与取消事项按 §2 的状态表处理，取消决定不因新会话、巡检或未完成清单而自动失效。

生命周期、互相引用和评论格式见 [TRACKING](TRACKING.md)。要点：

| 关联 | 位置 | 要求 |
|---|---|---|
| issue → 分支 | `task/<issue>/<slug>` | 一个 issue 一条 task 分支 |
| PR → issue | PR 正文「关联」段 `Closes #<issue>` | 与分支号一致，CI 的 `pr-contract` 核对 |
| issue → PR | issue 正文「实施」段 | 回填分支名、PR 链接、合并提交 |
| 进展 | issue 评论 | 按 [TRACKING](TRACKING.md) §3 的格式，每个阶段一条 |

**PR 合并进 `stage` 后，它 `Closes` 的 issue 必须关闭，task 分支与 worktree 必须清理**（2026-09-26 定的强制规范：「完成的pr管理的issue必须清理」）。`issue-lifecycle` 工作流自动关闭并在两边留「关闭」记录，`branch-hygiene` 删除远端 task 分支，本机 worktree 由开发者 `node scripts/task.mjs finish <issue>` 删。GitHub 自带的 `Closes #n` 只在合进 `main` 时生效，不能依赖它。自动化没关上的（工作流失败，或者 fork 来的 PR 合并时工作流没有写权限，#137），合并的人当场手工关闭，并按 [TRACKING](TRACKING.md) §3 的格式留「关闭」记录。已合并的分支不再提交；后续问题先提候选，确认后再建续作 issue。

## §2 正文内容

标题：`<模块>：<用户可见的症状或诉求>`，模块取「端」的标签名（portal / forum / admin / server / shared / deploy / docs）。

所有建单正文须有「确认依据」：Crosery 的确认原话或可追溯记录、获批的具体事项与边界；不能以 Agent 自述、测试通过或模板填充代替确认。候选阶段的方案按获批范围写入「方案」追踪记录，不把未经确认的实现选择当成既定需求。

### 缺陷

| 段落 | 要求 |
|---|---|
| 现象 | 实际看到了什么：原文报错、截图（直接拖进编辑框上传）、录屏；动画问题附逐帧图 |
| 复现步骤 | 最小路径，编号，每步写操作与看到的结果；偶发的写复现概率与已知条件 |
| 期望 | 应该是什么样 |
| 影响 | 谁会遇到、多严重、有没有绕过办法；决定优先级 |
| 环境 | 见 §3 |
| 验收条件 | 怎样算修好：可观察的结果 + 要在哪些尺寸 / 设备 / 环境看 |

### 需求 / 改进

写用户场景、范围和**不做什么**、接口 / 权限 / 数据影响、验收条件。描述问题与期望，不写实现方案（方案写在 PR 的「解决链路」或 issue 的「方案」记录里）。依赖升级说明动机、官方迁移来源和回退策略，不把「最新版」当成唯一理由。

严重性按真实影响区分：阻断核心流程、数据或权限风险为 P0；主要功能受损或已排期为 P1；其余 P2。未经复现的怀疑标为待确认，不以肯定语气写已证实漏洞。

### 改动类型标签（必填）

每个 issue 与它的 PR 都必须带至少一个「组:类」标签；一件事跨类就都带。共三组十一类，**组决定要交什么证明**：

| 组 | 标签 | 范围 | issue 里的证明 | PR 里的证明 |
|---|---|---|---|---|
| 界面 | `ui:layout` | 版式、响应式、溢出、竖屏适配 | 现状截图，注明视口与设备 | 改前改后截图（桌面与手机各一），不接受「无界面变化」 |
| 界面 | `ui:visual` | 配色、字体、图标、动画、3D 观感 | 同上；动画附逐帧图或录屏 | 同上 |
| 界面 | `ui:interaction` | 手势、键盘、焦点、触控目标、无障碍 | 同上；注明设备型号与操作路径 | 同上 |
| 界面 | `ui:content` | 界面文案与可见内容 | 同上 | 同上 |
| 功能 | `func:api` | 路由、请求响应约定、错误码、限流 | 「涉及接口」：方法 + 路径、请求响应约定、要补的接口测试 | 接口测试命令与真实输出，加对真实接口的请求（方法 + 路径）、状态码或 `requestId` |
| 功能 | `func:auth` | 登录、会话、角色与权限 | 同上，加身份维度 | 同上，加游客 / 成员 / 称号的通过与拒绝两条路径 |
| 功能 | `func:data` | 表结构、迁移、导入导出、存储 | 同上 | 同上，加迁移前后记录数核对与回滚路径 |
| 功能 | `func:external` | GitHub、发信商、CDN 等外部服务对接 | 同上 | 同上，加外部响应的隔离方式（只注入虚构响应） |
| 基础设施 | `infra:deploy` | 镜像、compose、环境变量契约、部署 | 命令与真实输出 | 命令与真实输出 |
| 基础设施 | `infra:ci` | 工作流、检查脚本、钩子 | 同上 | 同上 |
| 基础设施 | `infra:tooling` | 脚本、规范文档、测试基建 | 同上 | 同上 |

判定口径：看用户或调用方能直接看到什么变化。线上界面上看得到的归 `ui:*`；接口、权限、数据、外部服务的行为变了归 `func:*`；用户和调用方都看不到、只改部署、CI、脚本、文档的归 `infra:*`（文档类带 `infra:tooling`）。拿不准就多选，不要少选。既有的端标签（portal / forum / admin / server / shared / deploy / docs）、严重性（P0 / P1 / P2）和 `hot-fix` 照旧，与「组:类」并存。

- **谁来打**：issue 表单的「改动类型」下拉框选中的值会被 `issue-gate` 加成标签。用 `gh issue create`、API 建单的（包括别人的 Agent）没有表单，要自己带 `--label`；没带的，`issue-gate` 会按标题和正文的关键词在评论里推测并给出添加命令，**不会自动添加**，由提单人对照上面的口径确认。
- **没有标签、`ui` 没有截图、`func` 没写「涉及接口」**：`issue-gate` 加 `needs-evidence` 并评论缺什么，补齐后自动摘掉。带 `needs-evidence` 或检查不过的 issue 不得开工，`node scripts/task.mjs start` 会拒绝。这个标签既是开工门禁的依据，又是 `issue-gate` 要维护的状态，所以判定「补齐了没有」时不能把它自己算成缺失（#298）——否则标签一打上就永远摘不掉。没有接口变化的写「无接口变更：<理由>」，理由要有实际内容。
- **PR**：标签集合必须覆盖它 `Closes` 的 issue 的标签；`pr-contract` 按组核对「验收证据」与「验证命令与结果」，规则见 [PULL-REQUESTS](PULL-REQUESTS.md)。
- **生效范围**：编号 235 起的 issue 强制；更早的不回溯，也不因此补标签。

### 相关 issue（必填）

建单前在开放与已关闭的 issue 里按模块、关键词、错误信息搜过（`gh issue list --state all --search "<关键词>"`），正文「相关 issue」写 `#n` 和关系，或写「已搜关键词 X、Y，无相关」。按对方当前的状态处理：

| 已有的相似 issue | 怎么办 |
|---|---|
| 开着，同一件事 | 不新建，在原 issue 补充；想接手的在评论里说 |
| 开着，部分重叠 | 先提出独立验收范围与拆分候选；Crosery 确认后才新建，写 `Refs #n` 和边界；未确认不拆单 |
| 已完成，同一问题又出现，或留有尾巴 | 提出续作候选，附当前 `stage` 的复现证据，说明已做与剩余范围；Crosery 确认后建续作并写 `Refs #n`，不自动重开旧单 |
| 已取消（`not planned`） | 保留取消决定，不自动恢复、重开或换名建替代单；先向 Crosery 提出候选，获得明确恢复及建单安排后执行 |

`issue-gate` 会在新 issue 下评论标题相似的开放与已关闭 issue，只供核对，不替人判断，也不自动关闭、重开或改标签。

### 用 CLI / API 建单（没有表单时）

`gh issue create` 和 API 没有表单；先满足 §1 的 Crosery 确认门禁，再补齐字段和标签，与表单保持一致：

- **标签**：类型标签（缺陷 `bug`、需求 `enhancement`）、一个端标签、一个严重性（P0 / P1 / P2）、至少一个「组:类」改动类型标签，每个用一个 `--label`。标签必须已经存在于仓库；没有写权限的外部贡献者带的标签可能被 GitHub 忽略，此时 `issue-gate` 只能在评论里给推测，由有权限的人补。
- **正文**：
  - 两类正文都包含「确认依据」，保留具体事项的获批范围与可追溯记录。
  - 缺陷依次写：现象、复现步骤、期望、影响、环境、相关 issue、涉及接口（`func:*` 必填）、截图证明（`ui:*` 必填）、验收条件。
  - 需求依次写：现状与问题、期望的结果、范围与不做什么、相关 issue、涉及接口（`func:*` 必填）、验收条件。
- **图片处理与 Agent 防编造硬门禁**：
  - 用户在向 Agent 提单时，可以直接在会话中发送图片文件或粘贴截图；
  - **Agent 必须负责将收到的图片处理并上传至 GitHub 托管（生成 `https://github.com/.../assets/...` 或 Markdown 图片 `![...](https://...)`），再填入 Issue 正文**；
  - **严禁 Agent 自行编造裸文件名（如 `xxx.png`）或直接写入本地路径（如 `/tmp/...`）充当证据**。若未收到图片或未成功上传生成链接，**Agent 必须停下来主动向用户索要图片**，缺截图不许开工。
- **数据不全不提交**：拿不到环境、SHA、版本、`requestId`、响应原文、复现条件，或 `ui:*` 的截图时，先向请求人要，不编造，也不用「待补」占位凑字段；偶发问题标「待确认」。
- 正文以中文 [ISSUES.md](ISSUES.md) 为准，[ISSUES.en.md](ISSUES.en.md) 只是导航。

### 线上紧急缺陷（`hot-fix` 标签）

- **定义**：正式环境（`https://yangtzeu.work`）上线后出现的影响用户正常访问或核心功能受损的严重问题（如白屏、音视频流媒体阻断、认证/权限失灵、主流程阻断）。
- **打标**：必须打上 `hot-fix` 与 `P0` 标签。
- **确认**：紧急程度不豁免 §1，先核对 Crosery 对具体事项、操作范围和建单安排的批准。
- **协同约束**：遵循 [BRANCHING.md](BRANCHING.md)「线上紧急修复（Hotfix）规约」，从 `main` 快速修上线后，必须立即把修复提交合并回 `stage`，确保 `stage >= main`。各环境在配置与 Nginx 模板上必须严格同构，避免线上发生环境漂移。

## §3 环境与设备

**必填**：

- 分支与完整 commit SHA（`main` / `stage` / `task/<issue>/<slug>`），不写已退役的分支名；
- 站点与地址（本机 `127.0.0.1:5173`、预发布 `https://prev.yangtzeu.work`、正式 `https://yangtzeu.work`）；
- 页面显示的版本：正式 `X.Y.Z`，预发布 `X.Y.Z-rc.N@<sha12>`，能对应到发布 tag 时一并写上（见 [RELEASES](RELEASES.md)）。

**按问题类型补充**（与问题无关的不写，不为凑字段填）：

| 问题类型 | 需要的设备信息 |
|---|---|
| 布局、溢出、竖屏适配 | 视口尺寸（如 390×844）、设备像素比、横竖屏 |
| 3D、动画、帧率、卡顿 | 浏览器与版本、GPU / 机型、屏幕刷新率、是否前台真实浏览器（自动化浏览器会把动画页限在约 30Hz，不能用来判断帧率） |
| 触屏、手势、输入 | 设备型号、系统版本、浏览器 |
| 登录、权限 | 身份（游客 / 成员 / 哪个称号），**不贴会话、令牌或 cookie** |
| 接口、数据 | 请求路径、状态码、`requestId`；不贴完整请求头和真实数据 |

## §4 关闭与安全

完成关闭前，issue 上必须能查到对应 PR 与验证结果（自动「关闭」记录已包含）；不能仅因代码存在或构建成功关闭功能缺陷。Crosery 取消或决定不做的事项，以 `not planned` 关闭，记录决定依据，不写成已修复或职责完成。重复、被取代的 issue 先留真实「关闭」记录；替代单仍须先经 §1 确认。做完了就当场关；只剩外部等待的先记录等待原因并提出候选，由 Crosery 决定是否继续、拆分或建单，不自动关闭原单后生成替代单。每天巡检补关 PR 已合并还开着的 issue，给超期和缺记录的留言，不恢复取消事项（[TRACKING](TRACKING.md) §1）。

安全问题私下报告，不贴 Token、真实会话、完整请求头或生产数据库。
