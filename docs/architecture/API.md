# API 与数据契约

> 模块自有 Schema、明确错误语义和外部副作用约定。

状态：`current` · 更新：2026-10-31

方法路径的完整注册清单与已挂载 Schema 见[接口目录](catalog/routes.md)和[机器目录](catalog/catalog.json)。逐接口成功/失败响应、资源授权与数据副作用见[接口行为契约](../services/server/endpoint-contracts.md)。本手册继续维护跨接口约定；目录不把人工说明冒充已挂载的响应 Schema。

## 合同

各路由模块 contracts.ts 拥有本模块请求 Schema。http-contracts 提供公共参数验证；文档 ID 等非数字标识必须有模块例外。TypeScript 泛型不代替运行时校验，用户不得提供待执行的 Schema。

JSON 写操作定义类型、长度、范围、枚举与必填项，拒绝未知字段。分页为有界正整数，验证后转换。SQL 值仍参数化。

长度的数法分两层。Schema 的 `minLength` / `maxLength` 由 Fastify 自带的 Ajv 校验，按 Unicode 码点数（`app.ts` 给 Ajv 的选项只改了 `removeAdditional` 与 `coerceTypes`，`unicode` 保持默认），表情这类星平面字符算 1 个。以下既有路由的手工长度检查用 JavaScript 的 `String.length`，按 UTF-16 码元数，星平面字符算 2 个。一个字段两层都判断时两个上限都要满足。本文写的「N 字」按做判断的那一层算；路由里另有判断、按 UTF-16 数的是：论坛的游客回复正文（2000）、游客昵称（20）与成员昵称（30）（两者都按 NFKC 并去首尾空白之后数）、新建标签的名字（20，去首尾空白之后）、搜索词（100，去首尾空白之后），投递 `POST /api/portal/apply` 的全部字段（这个接口不注册 Schema），意见箱 `POST /api/feedback` 的正文（5–5000，去首尾空白之后）。比赛名称归一化后的最小长度及控制台名称、说明、URL 长度显式按 Unicode 码点计数，与 Schema 一致。其余只受 Schema 长度约束的字段也按码点：论坛标题写 120 个表情（240 个 UTF-16 码元）能通过，个人签名写 200 个表情也能通过；游客回复写 1001 个表情（2002 个码元）回 400 `content_too_long`。

## 接口族

portal 包括 /api/docs、/api/feedback、/api/portal/apply、/api/public/config、/api/public/departments；admin 包括 /auth/*（#274 review round 1 起只有登录与会话，GitHub 组织管理整组删除，见下方「端点清单」）；极客班控制台包括 `/api/console/*`（组织固定为 `CONSOLE_ORG`，按能力授权，见下方「极客班控制台」）；论坛接口 `/api/forum/*`（#57，见下方「论坛」与 [ADR-0004](../decisions/0004-forum-backend-in-core-server.md)）；对外授权 `/oidc/*`（#270，OpenID Connect 签发者，见 [对外授权与 GitLab 账号同步](../services/server/oidc.md)）；另有基础设施端点 `/healthz` 与 server 自身的 `/forum` 占位（逐条见下方「端点清单」）。`/api/forum` 下新接口没有注册的旧路径、`/auth/forum/*`、`/forum/u/*` 返回 410 legacy_forum_retired，不把旧接口映射成新接口。论坛页面是独立服务 `app/forum`（[forum 合同](../services/forum/README.md)）的静态产物，数据经同域 `/api/forum/*` 读写。开发态 `/forum/*` 跳转新首页，生产由 web 容器把 `/forum/*` 反代到 forum 容器；直连 server 的 `/forum` 返回 503。

核心 OAuth 回调和 sid 保留，oauth_state 保持签名和有效期检查；不再创建旧 forum_sid。官网、论坛、控制台共用这一个登录：官网菜单栏和论坛（快照模式）只经同域 `GET /auth/me` 读会话显示身份，退出调 `POST /auth/signout`，论坛没有自己的登录接口。Nuxt 的选择示例用户不进入此会话模型，不为其签发真实权限。开发专用 `/__geek_forum` 仅标记受控预览进程，明确 realAuthentication=false / serverPersistence=false、contentSource 和 snapshotConfigured（快照目录已配置，不是数据库连接），生产不提供该标记。dev 专用、仅 GET/HEAD 的 `/api/local-forum/state`（整份只读快照文档）和 `/api/local-forum/assets/:hash`（按索引提供附件，支持单段 Range，多段请求退化为完整正文）只在设置快照目录时存在，静态产物中没有；它们没有会话，也不是业务写接口。机器码：404 `local_snapshot_not_configured` / `asset_not_found` / `asset_missing_on_disk`，405 `method_not_allowed`，416 `range_not_satisfiable`，500 `asset_size_mismatch`，503 `invalid_document` / `invalid_state` / `invalid_asset_index` / `snapshot_unavailable`。dev 错误处理器会在错误体附带堆栈，这是这些路由不进生产的原因之一。真实的论坛接口在核心服务，契约与权限测试见下方「论坛」。

控制台意见箱 `GET /api/console/feedback` 返回 `{ items, counts }`，`items` 只含具名列 `id`、`category`、`content`、`contact`、`submitter_login`、`status`、`reply`、`replied_by`、`replied_at`、`created_at`（`app/server/src/lib/feedback-store.ts` 的 `AdminFeedbackItem`）；提交者 `source_ip`、`user_agent`、`submitter_id` 以及 `votes`、`updated_at` 只留在服务端，不下发浏览器。旧的 `GET /api/admin/:org/feedback` 已随 `/api/admin/:org/*` 整组删除（#274 review round 1），SQL 仍共用这份 `feedback-store.ts`。回归测试见 `tests/server/core.test.ts`。

## 端点清单

来源是 `app/server/src/app.ts` 与 `routes/**`。所有 POST/PUT/PATCH/DELETE 先经 `middleware/http-policy.ts` 核对 Origin 与 Fetch Metadata，不符返回 403 `invalid_origin`。`/api/*` 与 `/auth/*` 响应一律 `Cache-Control: no-store`，唯一的例外是头像与表情图片的 200 响应：论坛头像 `GET /api/forum/avatars/<hash>.webp`、账号头像 `GET /api/identity/avatar/<hash>.webp`、表情图片（按内容哈希寻址），以及 NANO 默认头像 `GET /api/identity/default-avatar/<版本>/<1–8>.png`（#343，地址带版本号），都长期缓存。表中「无」表示没有路由级限流（`@fastify/rate-limit` 以 `global: false` 注册）。路由级限流超额时都回 429 `{ error: "rate_limited", message: "操作太频繁，请稍后再试", request_id }`：`app.ts` 注册插件时把 `middleware/http-policy.ts` 的 `rateLimited()` 设成默认的 `errorResponseBuilder`，论坛自己按人、按 IP 数次数的限流（发帖、回复、头像）抛的也是它；全站游客回复的总量上限另回 429 `guest_replies_paused`（#191，回归测试 `tests/server/rate-limits.test.ts`）。按 IP 的限流、审计与投递里记的来源 IP 都取 Fastify 的 `req.ip`：部署环境 `TRUST_PROXY=2`，只信任宿主 nginx 与 web 容器 nginx 各自追加的那段 `X-Forwarded-For`，客户端自己带的最左边几段不算（见 [ENVIRONMENTS](../ops/ENVIRONMENTS.md) 与 [SECURITY](SECURITY.md)）。服务端的每个响应（包括错误、404 与静态文件）都带 `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`（`middleware/http-policy.ts` 的 `onSend` 钩子）。

被访问防护拦下的回应（#333，`middleware/shield.ts`）带 `notice` 字段，内容是 `lib/shield.ts` 的 `SHIELD_NOTICE`（「本次请求已被安全策略限制。」开头的一句中文告知，引用《网络安全法》第二十九条）：403 `ip_blocked`（`{ error, message, request_id, retry_after, notice }`）、429 任何来源的 `rate_limited` 与 `site_quota_exceeded`（在原来的体里多一个 `notice`）、蜜罐路径的 404 `{ error: "not_found", message, request_id, notice }`。正常回应不带 `notice`；`SHIELD_ALLOWLIST` 里的来源收到的 429 也不带。nginx 自己回的 429 体（`@yzgc_rate_limited`）也带同一句 `notice`。静态路径：`GET /.well-known/security.txt` 由 server 按 RFC 9116 回 `text/plain; charset=utf-8`，字段 `Contact`（从 `PUBLIC_ORIGIN` 拼出 `/?open=feedback`）、`Expires`（启动后一年）、`Preferred-Languages: zh, en`；被封禁的来源也照常拿得到。蜜罐路径（`/.env`、`/.git/`、`/wp-login.php`、`/wp-admin`、`/phpmyadmin`、`/actuator/` 等，见 `lib/shield.ts` 的 `HONEYPOT_PREFIXES`）经 web nginx 转给 server，命中即封禁，不计入任何接口的限流；server 按 nginx 的规整写法比较路径（解一次百分号编码、合并重复的 `/`、解析 `.` 与 `..`），`/%2Eenv`、`//.env` 同样命中，两层编码的 `/%252Eenv` 不算。`SHIELD_ENABLED=off`（开发环境）时计分、封禁、蜜罐与告知都不生效。

合成蜜罐是默认404的限时例外：管理员显式开启后，生产身份且基础防护开启时，未封禁的非豁免来源首次GET/HEAD命中固定敏感路径会得到200 `application/json`（HEAD无正文），同时被封禁。GET为 `{synthetic:true,service:"isolated-diagnostic",status:"restricted",data:{mode:"simulation",access:"none",records:[]},notice}`，不读取业务数据；响应禁止缓存及索引。关闭、到期和非读取方法恢复默认404，已有封禁仍403。详见 [SECURITY](SECURITY.md)「临时合成蜜罐」。

### 比赛信息发布合同（#238）

`competitions` 只存赛事事实；报名、组队与积分见下一节。新建必填 `name`、`kind`、`start_at`、`end_at`，可选 `signup_deadline`、`url`、`description`、`planning`（布尔，#278 重开，所有者 2026-10-25 提出比赛要有状态（规划中、进行中、已结束）；不填按不规划处理，默认 `false`）；PATCH 是非空字段子集，可另带 `offline`。名称去首尾空白后至少 2 个 Unicode 码点、最多 80 个；说明最多 1000 个码点；链接最多 500 个码点（控制台与 JSON Schema 同口径，扩展汉字不按两个 UTF-16 码元重复计数），所有类型都可不填，非空必须能解析为 HTTPS URL。请求 Schema 检查类型、范围与形状，路由调用 `competitionError` 校验名称、链接与时间关系；失败不写库、不记成功审计。五个操作同时挂载真实成功响应及共同错误 Schema，公开 DTO 不含内部字段，详见 `app/server/src/lib/competition-contract.ts`。

时间是 UTC 毫秒整数，范围 `0..8639999971200000`（Date 有效上限减北京时间八小时偏移）；结束不早于开始，报名截止不晚于结束。控制台新建的日期取北京时间整天；编辑时只 PATCH 修改过的字段，未修改日期保留 API 原始时分。省略 `url` / `signup_deadline` / `planning` 保留原值（创建时省略 `planning` 按 `false`）。显式 `null` 才清空 `url` / `signup_deadline`（`planning` 不接受 `null`，只是布尔）。`offline` 只影响公开可见性，重新上线保留原记录；DELETE 真删，重复删除 404。有未取消的报名后 PATCH 不能改 `kind`（409 `kind_locked`），已开放报名时不能把 `signup_deadline` 清成 null（409 `deadline_required`），有报名记录（含已取消）的比赛不能 DELETE（409 `has_signups`）。三种写操作与各自审计在同一事务内，审计失败回滚业务写入，GitHub 权限检查在事务前完成。

状态不入库，顺序为：`planning` 打开且 `now < start_at` → `planning`（压过下面几条，开赛前组织者还在筹备）；`now > end_at` → `ended`；有截止且 `now <= signup_deadline` → `registering`；`now >= start_at` → `ongoing`；尚未开始且没有报名截止 → `upcoming`；其余 → `closed`。未填截止不推定正在报名；过了开赛时间 `planning` 就不再生效，照后面几条算，不会把已经开赛的比赛卡在「规划中」。官网每 60 秒重算状态与排序，依赖响应里的 `planning` 字段（和 `start_at`/`end_at`/`signup_deadline` 一样现算的口径）；控制台重读时取服务端当前结果。匿名响应仅含表中列出的公开字段（含 `planning`，官网本地重算要用到它），控制台读取另含 `offline`；现有 `console.access` 允许读取，写入仍需 `competitions.manage`，UI 页面也按该管理能力显示。

### 比赛报名、组队与积分合同（#239）

门户的成员接口要求登录且是极客班成员（`middleware/require-member.ts` 按会话 `account_id` 判断，没有账号回 401 `not_signed_in`，不是成员回 403 `not_member`）。写操作统一要求「已开放报名且状态为报名中」：规划中（`status === "planning"`）回 409 `competition_planning`（#278 重开，压过下面两条，比「还没开放」「已经截止」更准确），未开放回 409 `signup_not_enabled`，不在报名中（含截止后）回 409 `signup_closed`；比赛不存在或已下线回 404。成员写操作每人每分钟 30 次，名单导出每分钟 5 次。请求体与响应由 [competition-contract.ts](../../app/server/src/lib/competition-contract.ts) 与两个 `contracts.ts` 挂载，逐项错误码见 [接口行为契约](../services/server/endpoint-contracts.md)「比赛报名、组队与积分」。

## 统一公开资料与身份资格（GitHub #271 回归）

公开消费者经 `lib/public-profile.ts` 只投影 `{username,display_name,bio,avatar_url}`：canonical `account_profiles` 优先；空昵称经 `identity-store.publicFallbacks()` 按账号批量只读当前登录名，不使用 `forum_users` 的旧缓存、不按邮箱合并，也不返回私有身份字段。头像是统一头像（#343，`lib/avatars.ts`）：上传的头像，否则 GitHub 头像（GitHub 自动生成的像素图不算，识别过的真头像给站内副本，还没识别时给 GitHub 地址），否则按 GitLab 主邮箱挑的 NANO 默认头像；每个带头像的接口给同一个人的都是同一个地址，详见 [server 合同](../services/server/README.md)「统一头像」。设备 userinfo 保留旧身份字段、增加上述公开字段；OIDC 的 `name/picture` 使用同一来源且本站头像转绝对地址，`preferred_username` 仍为登录名，pairwise sub 不变。论坛使用 camelCase 字段适配同一资料源；历史作者缺 canonical 行时保留原投影，不在批量读取中建档。

## geek 命令行令牌（#277）

`geek login` 换到的令牌（`POST /auth/device/token` 发的 `gk_…`）不止能调 `GET /auth/device/userinfo`：`middleware/bearer-auth.ts` 的 `onRequest` 钩子（挂在 `@fastify/cookie` 之后）从 `Authorization: Bearer` 读到有效令牌时，把账号按 cookie 会话同样的形状挂到 `req.session`、`req.via = "cli"`，下游的 `requireAuth`/`requirePermission`/`requireCompetitionAccess`/论坛的 `forumViewer` 等中间件不用跟着改，直接复用已经挂好的 `req.session`。规则：

- 同一个请求不能既带 `sid` cookie 又带 `Authorization: Bearer`，带了两种一律 400 `mixed_credentials`，不猜该信哪一个。
- 令牌本身无效、过期或账号已停用：不单独报错，`req.session` 不挂，下游按未登录处理（和 cookie 失效时的 401 一致）。
- scope 粗粒度拦截（节点级权限仍然交给 `requirePermission`/`requireWriter` 判定，这里不重复判断业务规则）：`/api/forum/*` 要 `forum`、`/api/teams/*`/`/api/me/applications` 要 `apply`、`/api/competitions/*`、`/api/me/competitions` 要 `competition`、`/api/public/gitlab/*` 要 `repo`；没有对应 scope 回 403 `insufficient_scope`（带 `scope` 字段）。`geek-cli` 客户端登记的 scope 是 `openid profile forum apply competition repo`（`lib/device-store.ts` 的 `DEVICE_CLIENTS`）。
- 令牌默认什么都不能用，只认：上面四类 scope 接口、`GET /auth/device/userinfo` 与 `POST /auth/device/revoke`、`/api/public/*` 的 GET/HEAD、`GET /api/console/me`（补部门及兼容旧版公开响应，不含真实姓名；新版公开资料优先 userinfo）。其余接口（控制台、账号页的改密码和绑邮箱、`/auth/me`、`/api/identity/*`、OIDC）带令牌一律 403 `cli_not_allowed`：令牌放在终端和 agent 的环境变量里，泄露的面比浏览器会话大，不能拿它改账号或做管理操作，`/auth/me`、`/api/identity/*` 还会回本人的真实姓名。
- 令牌不是一次登录，永远不算「刚登录过」：`require-step-up.ts`、账号页的 10 分钟窗口对 `via = "cli"` 一律不通过。
- 没有登录邮箱、或缺真实姓名和年级的账号不能用业务接口（#273、#280 的同一条规则，命令行没有浏览器会话可以读 `/auth/me` 的 `email_required`/`profile_required` 自己跳转，所以服务端这边单独挡一次），分别 403 `email_required`、`profile_required`（`lib/email-gate.ts` 的 `gateRefusal()`，先判邮箱再判资料）。`GET /auth/device/userinfo` 和 `POST /auth/device/revoke` 是身份接口本身，不算业务接口，不挡；`GET /auth/device/userinfo` 的响应额外带 `grade`/`grade_label`（按入学年份现算的年级，供 `geek whoami`/`geek status` 展示），但不带 `real_name`——命令行在任何接口下都拿不到任何账号的真实姓名，哪怕是本人。
- 操作记录：这类请求不管调用点自己传了什么 `surface`，落库时一律改写成 `"cli"`（`lib/activity.ts`）；每个状态码小于 400 的请求额外记一条 `cli.<method>`（`target_id` 是路径），和路由自己可能记的那条（比如 `forum.search`）一起留着，不是互相替代——控制台的操作记录（`GET /api/console/activity`）能直接按 `surface = "cli"` 筛出命令行发起的每一次登录与调用。

## 极客班控制台

`/api/console/*` 是极客班控制台的接口族，路由在 `app/server/src/routes/console/`，输入协议在其 `contracts.ts`（所有 body 与 query 都 `additionalProperties:false`，未知字段 400 `validation_error`）。组织固定为环境变量 `CONSOLE_ORG`（默认 `Yangtze-University-Geek-Class`），路径里没有 `:org`。

- **授权**：先 `requireAuth`，再 `middleware/require-capability.ts` 的 `requireCapability(...anyOf)`。同一请求只解析一次身份（`req.access`）。缺能力返回 `403 { error: "missing_capability", capability, any_of, message }`：`capability` 是 `anyOf[0]`，`message` 为「需要「{能力中文名}」权限」。不是成员的账号没有任何能力。按钮只是提示，授权只在服务端。
- **身份**：`GET /api/console/me` 返回 `{ login, avatar_url, org, provider, site_role, github, title, titles, capabilities, head_of, email_required }`（#262 第四期；`email_required` 同 `/auth/me`，#273）。`provider` 是这次的登录方式（`github` / `email` / `google`）；`site_role` 是账号的站内角色（`admin` / `member` / `null`），不论用哪种方式登录，能力都按它和称号给；`github` 是控制台的 GitHub 页面这次经什么接 GitHub：`app`（服务器的 GitHub App）、`session`（本人的 GitHub 会话）或 `none`（没接上，那些页面回 409 `github_not_connected`）。`TitleView = { id, label, tag, icon, tone, department, source, assignment_id }`，`source ∈ assignment | site | none`；`capabilities` 按能力清单顺序。能力模型与站内角色规则见 [SECURITY](SECURITY.md)「权限只认极客班账号」。
- **GitHub 调用**：#274 review round 1 起整个控制台不再调用 GitHub（`lib/github-connection.ts` 已删除，见 [SECURITY](SECURITY.md)「权限只认极客班账号」）：GitHub 登录只用来认人，成员资格、站内角色与能力只认账号在新权限引擎里记的（`perm_members`），指派按极客班账号或登录名找本站认识的人。
- **契约细节**：投递路径参数叫 `:application_id` 并按 UUID 校验（`:id` 会被公共校验强制成数字）；`export.csv` 是静态路由，优先于 `/:application_id`。`limit` 1–200（意见箱 1–500），`offset` 0–99999999，`q` ≤100 字，按 LIKE 匹配姓名、班级、邮箱并转义 `%`、`_`、`\`。CSV 以 `= + - @ \t \r` 开头的单元格前加 `'`，防表格公式注入。
- **状态与发信**（#148、#204）：投递状态是 `received`（已收到）、`interview`（待面试）、`accepted`（已录取）、`rejected`（未通过）、`cancelled`（已取消）五个；清单、列表 `counts`、概览 `by_status` 与 CSV 的 `status` 筛选使用同一份枚举。`reviewing` 已退役（启动时改回 `received`，审核历史里保留原值）。取消保留简历和历史、不生成邮件，不撤回此前已排队或已发出的其他邮件。其余改状态写的信先进队列，由服务进程里的循环发出，接口不等发信结果；`MailSummary` 显示每封信是等着发、已发出、放弃了还是没发（`skip_reason`：`mail_disabled` 没配置发信商，`not_allowlisted` 发信白名单里没有这个地址，`rate_limited` 全站这一小时的「已收到」到了上限；`recipient_limited`、`source_limited` 是 #148 的旧记录，#169 起不再出现）。队列、重试、白名单与隐私见 [mail](../services/server/mail.md)，回归测试见 `tests/server/mail-outbox.test.ts`。
- **邮件模板**（#285）：四类信的内容是库里的模板，每类可以有多套、有且只有一个默认；改状态的 `template_id` 选哪一套，不传用默认。模板用 `{{变量名}}` 写变量，清单固定、由 `GET /api/console/mail-templates` 的 `variables` 返回，未知变量和别的类别的变量保存时回 400 `template_invalid` 并指出位置。管理、预览和向测试邮箱试发要节点 `mail.template.manage`（默认只有站长），写操作和试发要刚登录过；试发只发到请求里填的一个地址、不改任何投递记录，每账号每小时 10 封、全站每小时 30 封。模板规则、变量清单和限量见 [mail](../services/server/mail.md)「邮件模板」。
- **审计**：所有控制台写操作以及投递的查看、导出都以 `org = CONSOLE_ORG` 写审计。审核备注只存 `application_reviews`，不进审计。
- **Mock**：开发预览 `?__data=mock` 覆盖控制台所有 GET（`?__persona=` 切换身份），写请求照旧返回 501 `mock_read_only`，不伪造写成功。例外是两个不写任何数据的 POST，邮件模板的 `preview` 和投递详情的 `letter-preview`：开发预览里按样板数据真的渲染，未知变量同样回 400 `template_invalid`，编辑页的实时预览才有东西可看；`test-send` 和其它模板写操作仍是 501。
- 回归测试见 `tests/server/console.test.ts`。

## 论坛

`/api/forum/*` 是论坛前端（`app/forum`）的数据接口（#57，[ADR-0004](../decisions/0004-forum-backend-in-core-server.md)），路由在 `app/server/src/routes/forum-api/`，输入协议在其 `contracts.ts`（body 一律拒绝未知字段），存储见 [数据模型](../services/server/data-model.md)「论坛」。请求与响应都是 JSON（头像上传除外）；写请求走同一个 Origin 校验。

- **身份**：有效会话按 `account_id` 认人并续用原论坛用户；有 GitHub id 时兼容 `m<GitHub id>`，没有时使用既有 `a<序号>`。`viewer.kind=member` 是已登录账号，不等于 OIDC member/alumni 资格：registered、邮箱/Google 账号都不是游客，但写权限仍逐节点判。没有有效会话才是游客。角色、部门和称号由权限引擎的当前分组刷新，公开用户名/昵称/简介/头像按上节投影，不把旧 GitHub 角色列作为权限事实。
- **授权**：发话题、回复和互动分别由服务端检查 `forum.topic.create`、`forum.reply.create`、`forum.react`；版务检查 `forum.moderate.*` 并带目标分类 scope。scope、会话或按钮显示都不代替权限节点；资格/条目到期后暖缓存必须在下一请求失效。普通注册用户可按读取节点读，不能因为已登录自动写；判定不向 GitHub 查询组织角色。
- **返回的 `state`**：与 `app/forum/app/data/types.ts` 的 `ForumState`（`version: 1`，`seededAt: 0`）同形，另加 `viewer: { userId, kind: "guest" | "member", capabilities, level, nodes }`（`capabilities` 只含 `forum.*`；`level`、`nodes` 是 #276 加的分级可见等级与写权限节点子集，见下文「#276」一节「看的人」）。**帖子不带正文**（#156）：`posts[]` 每条只有 `id`、`topicId`、`authorId`、`createdAt`、`editedAt?`、`replyToPostId?`、`likeUserIds`、`deleted?`，加上服务端截好的一行纯文本摘要 `excerpt`（Markdown 压成一行，代码块去掉、链接只留文字；超过 200 个 UTF-16 码元时取前 200 个再加一个「…」，所以最长 201，`lib/forum-rules.ts` 的 `postExcerpt`）；列表、书签页、个人页的摘要都读它，进话题页再取 `GET /api/forum/topics/:topic_id/posts` 里的正文。话题、用户、通知、书签、关注的形状不变。`users[]` 每项另有 `kind: "member" | "guest" | "official"`；`notifyPrefs` 只有看的人自己的是真实值，别人的一律是这一类用户的初始值（成员全开，游客与官方账号全关），字段照常存在；已有 canonical 档案的账号头像优先 `/api/identity/avatar/<hash>.webp`、否则回退绑定头像；缺档案的历史作者沿用旧 `/api/forum/avatars/<hash>.webp` 或原绑定头像，游客与官方账号保留原形状。`notifications`、`bookmarks` 只含看的人自己的，游客两者都是空数组；`follows` 不按看的人过滤，是全站所有的关注关系（谁关注了谁对所有人公开，游客也拿到全部，`lib/forum-store.ts` 的 `state()`；`tests/server/forum.test.ts` 的 `toggles follows, refuses self-follows and notifies once` 用例里，游客读 `state` 拿到全部 2 条关注），要「我关注的」由客户端按 `followerId === viewer.userId` 筛。分类、精选标签来自 `app/forum/content/curation.json`（按 `categoryOrder` 排），后面接用户建的标签。删除是软删除：`deleted: true`、`content: ""`（`/state` 里的记录没有 `content`，删除只体现在 `deleted: true` 与清空后的 `excerpt`）。
- **写接口的回答**（#145）：不再是整份 `state`，是 `{ changes, viewer }`（发话题另带 `topicId`、`postId`，回复另带 `postId`）。`viewer` 与 `state` 里的相同；`changes` 只有这次写入改动的记录，按类放在 `users`、`tags`、`topics`、`posts`、`notifications`、`bookmarks`、`follows` 里（没有的类不出现），每条与同一个人此刻读 `state` 得到的那条完全一样，可见性规则也一样（#156：帖子这一条在 `/state` 里只有摘要；只有发帖、回复、编辑、删除这四种改了正文的写入多带 `content`，其余写入的帖子记录与 `/state` 里的同一条逐字节相同，所以赞一条长帖不会再带回它的正文）：别人的 `notifyPrefs` 是初始值，别人的通知和书签不会出现。取消的书签和关注只有两端的编号，放在 `removed.bookmarks: [{ userId, postId }]`、`removed.follows: [{ followerId, followeeId }]`。成员的回答总带自己的用户记录（每次请求都会刷新角色、称号和 GitHub 头像）。每个接口带哪些记录写在下表「成功」一栏，也写在 `routes/forum-api/contracts.ts` 的 `ForumWriteResponse`。前端按编号把 `changes` 并进手里的状态，见 [forum 合同](../services/forum/README.md)「服务端模式」。
- **编号**：旧帖 `t<n>`（<1000）与首帖 `body-<n>`，新话题从 `t1001`、新帖子从 `p10001` 起，游客 `g<n>`（用户名 `guest-<n>`），通知 `n<n>`，新标签 `tag-<n>`；都由数据库计数器得出。
- **按 IP 计数**：游客回复限流、浏览去重、`state` 与浏览接口的限流按 `req.ip` 计；IPv6 按 /64 前缀计（`lib/forum-rules.ts` 的 `ipSubject`），IPv4 映射的 IPv6 按 IPv4 计。
- **昵称**：游客昵称与成员的 `displayName` 用允许清单（`lib/forum-rules.ts` 的 `isAllowedName`，先做 NFKC，全角字母和数字变成半角；存的是 NFKC 之后去掉首尾空白的写法，不换行空格、全角空格存成普通空格）：只收汉字、平假名、片假名、韩文（只收合成好的音节 U+AC00–U+D7A3；单独的字母和显示成空白的填充字不收，按顺序写的字母 NFKC 会合成音节）、拉丁字母里的基本拉丁、拉丁-1、拉丁扩展 A、拼音声调字母 U+01CD–U+01DC 与 U+1E00–U+1EFF、ASCII 数字、长音符 ー，以及空格和 `- _ . · ・ '`；空格不能在首尾或连着用，至少要有一个字或数字。其它都拒绝：看不见的字符、表情、西里尔与希腊等其它文字、IPA 与小型大写这类形近拉丁字母；NFKC 之后 `µ` 是希腊字母，也拒绝。错误码是 `invalid_guest_name` / `invalid_display_name`，`message` 是「昵称只能用汉字、字母、假名、韩文、数字、空格和 - _ . · ・ ' 这几个符号，空格不能连着用」，空名字另有长度提示。规则只管新写入，库里已有的昵称不改；成员提交的 `displayName` NFKC 并去掉首尾空白后，和库里现存的（同样处理）相同，就当没改，不查也不写，不合现在规则的旧昵称不会挡住改签名、网站。判断重名时两边都按 `nameKey` 归一：NFKC、不分大小写、去掉附加符号（é 和 e、が 和 か 算同一个），形近字折成同一个（ı 和 i、ĸ 和 k，片假名カ ニ ロ エ ハ タ ト ー 和汉字力 二 口 工 八 夕 卜 一，平假名へ和片假名ヘ），再去掉所有空白和 `- _ . · ・ '`（「极 客班」「极客班.」和「极客班」、「阿・凡提」和「阿·凡提」算同一个）。
- **错误体**：路由抛出的业务错误、Schema 校验失败和限流都经统一错误处理，体是 `{ error, message, request_id }`，`message` 是中文，可以直接给用户看。Schema 校验失败是 400 `validation_error`（提示写明哪个字段），路径里的编号格式不对也是 400。例外：403 `invalid_origin`、头像超过 2MB 的 413 `avatar_too_large`、旧路径的 410 `legacy_forum_retired` 是直接回的，没有 `request_id`；Fastify 自己拒绝的请求（例如带 `Content-Type: application/json` 的空请求体）`error` 是 Fastify 的错误码（`FST_ERR_CTP_EMPTY_JSON_BODY`），`message` 是英文。

### #276：分级可见、表情、上传、访客翻页上限、@ 自动补全、控制台论坛管理

CONTRACT-276 在上面这套 #57/#156/#274 的基础上加了六件事：话题分级可见（`public < registered < member`，生效值 `COALESCE(话题自己的设置, 分类设置, 'public')`）、去掉游客回帖（上表 `POST /api/forum/posts` 已更新）、表情包与表情回应、帖子正文的图片上传、@ 提及自动补全、控制台「论坛管理」（分类可见范围、表情包/表情维护）。身份判定、`changes`/`viewer` 的形状延续上文，游客 `kind` 不变；下表的「谁能用」里 `forum.react`、`forum.upload.image`、`forum.reply.create`、`forum.topic.create` 都是迁移种子只发给 `level.member` 的权限节点（见 [data-model](../services/server/data-model.md)「论坛」），`forum.moderate.edit` 按话题所在分类限定 scope（部门组天然带这个 scope）。

- **看的人（viewer）**（团队负责人追加）：`kind` 只分 `"guest"`/`"member"` 两档，分不出「登录了但不是极客班成员」和「成员」，前端没法判断谁能发话题、回复、点表情、传图——`viewer` 另加两个字段：`level: "public" | "registered" | "member"` 是 `levelOf()` 按权限节点 `forum.read.member`/`forum.read.registered` 判出的分级可见等级，游客恒为 `"public"`；`nodes: string[]` 是 `["forum.topic.create","forum.reply.create","forum.react","forum.sticker.use","forum.upload.image","forum.moderate.edit"]` 里这个账号持有的子集（按 `permissions.check(accountId, node)` 逐条判定），游客恒为空数组。两个字段只做按钮显隐的参考，真正能不能操作仍由 `requireWriter`/`canModerate` 判定，前端不能只信这两个字段就放行写操作。
- **分级可见**：`GET /api/forum/state`、`GET /api/forum/search`、`GET /api/forum/topics` 三个列表接口按身份在 SQL 层过滤看不到的话题与帖子（不是查出来再筛），`/state`、`/search` 的响应形状不变，只是看不到的那些整条不出现；直接按 id 取单个话题的帖子（`GET /api/forum/topics/:topic_id/posts`）或回复它改为先判可见范围，看不到时访客 401 `unauthenticated`（带 `need`）、登录但不够 403 `forbidden`（带 `node`、`need`），响应体不带标题或正文；不存在的话题仍是 404，和「看不到」用状态码区分。`PATCH /api/forum/topics/:topic_id/visibility` 改话题自己的可见范围（`null` 跟随分类）。
- **访客翻页上限**：`GET /api/forum/topics` 是新的话题列表读接口（游标分页，取代浏览器端翻页），第一页（不带 `cursor`）免费，访客从第二页起按天（北京时间）最多翻 10 页，超了 429 `rate_limited`（`bucket: "forum.visitor.pages"`）；登录用户不限。
- **表情**：`GET /api/forum/stickers` 公开列表，`PUT`/`DELETE /api/forum/posts/:post_id/reactions/:sticker_id` 需要 `forum.react`，响应只回这条帖子的表情聚合 `{ reactions: [{ stickerId, shortcode, url, count, mine }] }`（camelCase，和帖子记录里的 `reactions` 字段同一套对象，不是 CONTRACT-276 §4 原定的 `sticker_id`，偏差记在 DECISIONS-LOG），不是整份 `changes`；`mine` 按当前看的人是不是也回应过这条表情判定，游客恒为 `false`。
- **上传**：`PUT /api/forum/uploads` 需要 `forum.upload.image`，PNG/JPEG/WebP 统一转 webp、GIF 动图原样保留，≤5MB、≤4096×4096。
- **@ 自动补全**：`GET /api/forum/users/suggest` 只要求登录（不要求 `level.member`），按用户名/昵称前缀匹配，不回邮箱。
- **控制台论坛管理**：`/api/console/forum/*` 走 `requirePermission` + 写操作 `requireStepUp`（CONTRACT-274 §5 的 10 分钟窗口），和论坛前台接口是两套不同的鉴权。

## 加入我们（投递）端点

`POST /api/portal/apply` 是官网「加入我们」（`/join-us` 信封页）的写接口：#274 SPEC §3 起要先登录并持有权限节点 `apply.submit`（`level.registered` 天然有，没登录或是访客回 401/403）——不再是匿名表单；带设备 cookie `yugc_apply_device`（没有或不像我们发的就发一个新的，httpOnly、`SameSite=Lax`、`Path=/api/portal/apply`、一年，只用来数投递次数）；成功时写一行 `applications`（含来源 IP 与 User-Agent）和一条 `audit_logs` 审计。前端页面与本节同批发布，字段名与 PoW 摘要输入属于跨端契约，改一端必须同时改另一端。**#275 待办**：官网表单本身还没改成先登录再投递，部署前端要确认这两边同步上线，否则匿名访客会在真实环境看到一直 401。

| 请求字段 | 约束 |
|---|---|
| `name` | 必填，trim 后 2–40 字符，禁止控制字符 |
| `className` | 必填，trim 后 2–40 字符，只允许中文、字母、数字、空格、`·`、`-` |
| `email` | 必填，≤120 字符，形如 `x@y.z` |
| `strengths` | 必填，trim 后 10–2000 字符 |
| `website`、`homepage`、`url_ref` | 蜜罐字段（`middleware/pow.ts` 的 `checkHoneypot`）：任一非空即按机器人处理；前端只渲染隐藏的 `website` |
| `pow` | `{ timestamp, nonce }`；摘要输入固定为 `apply:<trim 后 name>:<trim 后 email>`，难度取 `/api/public/config` 的 `pow_difficulty` |
| `turnstile_token` | 只在 `/api/public/config` 的 `turnstile_site_key` 非空时校验，空字符串视为未提供 |

响应与错误码：

- `401 { error: "not_signed_in" }` / `403 { error: "forbidden", node: "apply.submit" }`：没登录，或登录了但没有这个权限节点（目前只有访客会落到这一档，`level.registered` 起都有）。
- `403 { error: "apply_closed", message: "招新暂未开放" }`（#284）：控制台把招新总开关关了。这一步在权限节点之后、蜜罐与字段校验之前，所以没登录的请求仍先回 401；被拒的请求不写 `applications`、不占任何一条每日额度、不发「已收到」的信、不下发设备 cookie，由 `middleware/http-policy.ts` 记一条 outcome 为 `denied`、动作为 `http.apply_closed` 的操作记录。路由级 5 次/分钟的限流在更早一步，被拒的请求照常计一次。重新开启后立刻恢复，不用重启。
- `201 { id, submitted_at, message, quota: { apply_left_today, apply_daily_limit } }`：`id` 为 UUID，`submitted_at` 为毫秒时间戳，`message` 为中文提示，`quota` 是这次写入之后的剩余额度（`apply_daily_limit` 为 `-1` 表示不限，极客班成员）；响应不回显 `strengths` 或其它请求字段。同时往发信队列写一封「已收到」的信（`event_key` 为 `application:<id>:received`），信里有报名信息和特长原文；信写不进队列时只记日志，投递照样成功，响应不变。蜜罐命中不写信、不计入额度。
- `400 { error, fields }`：字段校验失败的逐字段中文错误，`fields` 只包含出错字段，`error` 等于首个出错字段的提示；校验失败不写库、不计入额度。
- `400 { error }`：PoW 与 Turnstile 失败沿用公开表单既有形状（`防滥用校验失败，请刷新页面重试`、`人机验证失败，请刷新重试`）。蜜罐命中不返回 400，见下文。
- `429 { error: "rate_limited", message, request_id }`：路由级限流，5 次/分钟/客户端。
- `429 { error: "rate_limited", bucket: "apply.daily", message, retry_after }`（#169，#274 改成按账号为主）：账号当天（北京时间零点重置）的投递额度（`meta.limit.apply.daily`：注册用户 3 份、极客班成员不限）、来源 IP（IPv6 按 /64）当天 10 份、设备当天 5 份，三条线任一超限都回这个形状，不区分是哪一条（不给探测哪条更松的机会）；`retry_after` 是到下一个北京零点的秒数。这一份不落库、不写信、不计入任何一条线的额度。计数见 [数据模型](../services/server/data-model.md) 的 `limit_events`（`application_limits` 表已弃用，只留历史数据）。

边界行为：蜜罐检查在字段校验之前，命中时返回与成功完全一致的 `201` 形状但不落库，不向脚本暴露陷阱；公开表单通用的蜜罐 400 `请求被拒绝` 在本端点走不到。字段约束在路由内单一校验层实现，该端点不注册 `contracts.ts` body schema；除三个蜜罐字段外，未知字段被忽略而不是让投递失败。落库与审计见 `app/server/src/routes/portal/apply.ts`、[server 合同](../services/server/README.md) 与 [数据模型](../services/server/data-model.md)：审计动作 `application.received` 记录目标 id、来源 IP（`ip` 列）与 `account_id`，details 只含脱敏邮箱、班级、`name_length` 和 `strengths_length`，不记姓名与完整 `strengths`。回归测试见 `tests/server/applications.test.ts`、`tests/server/rate-limits.test.ts`、`tests/server/mail-outbox.test.ts`。

## 错误

校验 400、未登录 401、权限/来源 403、不存在 404、冲突 409、请求体超限 413、不支持的 Content-Type 415、频率限制 429、服务异常 5xx。错误体都有 `error`，多数还有 `message`；不得暴露 Token、SQL、完整外部响应或堆栈。

`request_id`（Fastify 的请求编号，与服务端日志里的 `requestId` 相同）只出现在经 `middleware/http-policy.ts` 错误处理器输出的错误里：路由抛出的错误（论坛的业务错误、邀请预占的 409）、Schema 校验失败、Fastify 自己拒绝的请求、限流、GitHub 上游错误，以及上游 401 结束会话时的 `session_expired`。路由或中间件直接回复的错误没有 `request_id`，常见的有：401 `not_signed_in`；`requireAuth` 发现 `sid` 已失效时的 401 `session_expired`（只有 `error`，没有 `message`）；403 `invalid_origin`、`missing_capability`；410 `legacy_forum_retired`；413 `avatar_too_large`；429 `rate_limited`（bucket `apply.daily`）；控制台各路由自己回的 400、403、404、409（如 `invalid_status`、`letter_required`、`admiral_required`、`not_found`、`status_changed`、`assignment_exists`）；`/api/feedback`、`/api/portal/apply` 与管理端旧路由回的 `{ error: <中文句子> }`（这类 `error` 不是机器码）。没有注册的路径：服务端托管前端产物时回 404 `{ error: "not_found" }`；不托管时（server 镜像里没有前端产物）是 Fastify 默认的 404 `{ message, error: "Not Found", statusCode: 404 }`。

限流的 429 约定是 `{ error: "rate_limited", message: "操作太频繁，请稍后再试", request_id }`。

访问防护（#333，`lib/shield.ts`、`middleware/shield.ts`）两种新的拒绝：被封禁的 IP 在任何路由之前收到 403 `{ error: "ip_blocked", message, request_id, retry_after, notice }`（`retry_after` 为剩余秒数，`/healthz` 与 `/.well-known/security.txt` 不拦）；全站北京日上限用完收到 429 `{ error: "site_quota_exceeded", bucket, message, retry_after }`（`bucket` 是 `site.email.daily`、`site.register.daily`、`site.feedback.daily`、`site.device_code.daily` 之一）。两者都带 `Retry-After` 头。前端判断 `error` 即可，`message` 是给人看的中文。计分不改任何接口的回应：验证码过期、已用或没有挑战（`code_expired` 且没有真的比对）不加登录失败分；外站让浏览器发来的请求（`Sec-Fetch-Site: cross-site` 且没有 Origin 或 Origin 不是本站）不触发蜜罐、不按状态码计分，但限流、全站上限、Origin 核对与生效中的封禁照旧。被 403/429 拦下的请求在操作记录里带 `meta.method`、`meta.route`（匹配到的路由模板，没匹配到为 `null`）与 `meta.status`，按它们分行合并，不记原始路径与查询串。

第一层限流在 web 容器的 nginx（`app/web/Dockerfile`）：`/api/`、`/auth/` 超额回 429 `{ error: "rate_limited", message }`，不带 `request_id`（nginx 直接回复）。路由级限流与论坛自己计数的限流均由 `middleware/http-policy.ts` 的 `rateLimited()` 产生（#191）；论坛另有 429 `guest_replies_paused`（全站游客回复到了上限），投递另有 429 `rate_limited`（bucket `apply.daily`，北京时间每天 0 点重置）。

路由未自行捕获的 GitHub 上游错误（Octokit 只带 `status`）由 `app/server/src/middleware/http-policy.ts` 统一处理：上游 4xx 按原状态码返回，机器码 `upstream_rejected`，message 是按状态码给出的中文说明，不回显上游原文；上游 5xx、无状态码或状态码无效的异常一律脱敏为 5xx `internal_error`。例外是带会话（`sid`）的请求用会话里存的令牌调 GitHub 遇到上游 401：401 说明它已经失效（被撤销或被收回），于是删掉会话、清 `sid` 与 `forum_sid`，回 `401 { error: "session_expired", message: "登录已失效，请重新登录" }`，同一会话只审计一次 `auth.session_rejected`（#164）；之后带着旧 `sid` 的请求按未登录处理。#274 review round 1（blocker）起，登录之后的业务路由（`/api/forum/*`、`/api/console/*`、`/auth/me`）再也不会用会话令牌调 GitHub（那条路径——`access.resolve()` 的组织角色实时查询——已经整段删掉，见 [SECURITY](SECURITY.md)「权限只认极客班账号」），所以这条「上游 401 结束会话」目前没有业务路由会触发，只作为通用基础设施留着给以后真的调 GitHub 的路由用，回归测试改成一个独立的合成路由，见 `tests/server/upstream-errors.test.ts`；`GET /api/join/:token`、`POST /api/join/:token`（公开邀请链接）、`lib/github-connection.ts`（服务器 GitHub App 接入）、`lib/invite-reservation.ts` 都已随 CONTRACT-274 §8 删除，`github_connection_failed`、`github_not_connected`、`invite_unavailable`、`invite_pending_review`、`tests/server/invitations.test.ts`、`tests/server/github-connection.test.ts` 一并作废，不再出现在任何响应里。

## 幂等与验证

核心邀请按链接与标准化收件人记录，成功重试复用结果；明确失败补偿，未知结果保留额度并待核对。PR 合并带 head SHA；评论并关闭先确认，再依次等待成功。旧论坛软删除策略已经退出运行，其历史测试不能作为新论坛后端行为证明。

测试覆盖正常、非法字段、未知字段、边界、角色、缺失资源和并发。Mock 是只读预览，不伪造写成功。新 DTO 使用具名类型；复杂上游宽类型限制在适配边界并说明理由。
