# Security — English overview

> English navigation companion; the Chinese document is the canonical current specification.

Status: current. Updated: 2026-09-26.

See [SECURITY.md](SECURITY.md) for the complete current document. This overview does not define a second rule set.

The core portal/admin retain server authentication. Sign-in is one GitHub login shared by portal, forum and console; the callback checks the user's own membership in `CONSOLE_ORG` and creates a session only for active members. Non-members and pending invitees get no session (audited as `auth.signin_denied`, and the app's grant is revoked on a best-effort basis) and return to the starting page with `?signin=not_member|invite_pending`; GitHub errors return `?signin=failed` and are never treated as "not a member". The owner completed a real GitHub sign-in on the local preview on 2026-09-25; preview and production are not verified. Feedback summaries and admin replies are readable anonymously through `GET /api/feedback/public`, so feedback text is treated as public; résumé submissions have no read endpoint. The adopted Nuxt/TuffEx forum uses the same site-wide login (the upstream mock identity picker remains only in the upstream verification runs and the local sample preview) and has no backend yet, so it is not a production security boundary. Legacy forum APIs return 410 and the old forum database is not opened. The production and preview stacks must stay fully isolated (directory, compose project, ports, volumes, secrets, domains) with host-only cookies, and runtime `.env` secrets are injected by CI/CD only — repository templates keep secret fields empty. Production rollout and operational verification require separate authorization and evidence.

The console (`/api/console/*`) adds a title → capability layer on top of GitHub organization roles. Titles and departments are data: each title's label, tag, icon, tone, description and permission bundle live in the `titles` table, seeded once from the defaults in `app/server/src/lib/roles.ts` (`INSERT OR IGNORE`, so the database wins after the first start) and edited in the console through `PATCH /api/console/titles/:title_id` by whoever holds `roles.manage` (audited as `title.update`); the two top titles (提督 and 舰长) can only be edited by the 提督 (403 `admiral_required`), otherwise a 舰长 holding `roles.manage` could widen their own bundle. Only the title ids, their ranks, the capability list, the tone palette and the icon list are fixed in code. The default names follow the owner's starship scheme of 2026-09-25: 提督 (`admin`), 舰长 (`captain`), 队长 (`head`, shown as `{部门} · {label}`), 舰员 (`member`; `{部门} · {label}` inside a department), 领航员 (`alumni`), 乘客 (`guest`, not signed in, read-only). The owners of the GitHub organization are the 提督 automatically and always hold every capability; the old bootstrap stand-in ("org admins act as captain until one is appointed") is gone. The server enforces that the 提督 bundle is always everything, the 乘客 bundle is always empty, and `roles.manage` fits only the 舰长 bundle. Only the 提督 or the current 舰长 can appoint or transfer the 舰长; the 舰长 row can be removed by the 舰长 themself or by the 提督. Holders of `roles.manage` can delete a department; its heads and crew lose that department title in the same transaction (audited as `department.delete`), and the default departments are seeded only on the first start, so a deleted one does not come back after a restart. `GET /api/console/people` lists every organization member with their titles (holders of `roles.department.manage` see the whole list too, not just their department), and the anonymous `GET /api/public/org` publishes the display half of titles and departments (no bundles, no people) for the portal and the forum, which fall back to built-in defaults when it cannot be read. The forum backend (#57, `/api/forum/*` in the core server, [ADR-0004](../decisions/0004-forum-backend-in-core-server.md)) enforces the same `forum.*` capabilities server-side; guests may read and reply (proof of work, honeypot, per-IP limits with IPv6 counted per /64, a site-wide cap of 200 guest replies an hour, names limited to an allowlist of Han, common Latin letters, kana, Hangul, digits and a few separators) but not open topics, and a session whose owner is no longer an organization member is treated as a guest. Every per-IP limit and every recorded client IP relies on `TRUST_PROXY=2` (the host nginx and the web container nginx), never on the client-supplied leftmost `X-Forwarded-For`.
