## 摘要

GitLab 的统一登录在 10-28 前写死了预发布的签发者，正式站成员没有可用的入口；修复过程中，正式与预发布两套成员同步在 10-29 同时开着，给 6 名已有号的成员又建了重复号，签发者改接因此卡住一天。比赛 10-21 开赛，这段时间参赛者只能在 GitHub 提 issue 和 PR。10-30 02:45 改接完成，成员用正式站统一登录回到自己原来的 GitLab 号；GitHub 上的 15 条参赛 issue 已按原作者迁回 GitLab。

## 影响

- 正式站成员：10-28 之前从 GitLab 登录走的是预发布的账号体系；10-29 白天之后，6 名成员在 GitLab 上同时有原号和 `_yz` 重复号。没有数据丢失，重复号从未登录过。
- 比赛：10-28 21:34 到 10-29 15:23，3 名参赛者在 GitHub 提了 15 条 issue、5 个 PR，GitLab 上的计分收集器看不到它们。
- 预发布：不受影响。

## 原因

直接原因有三个，分别在不同的一天暴露：

1. 签发者写在 GitLab 配置片段里，而且写的是预发布的地址。正式站从来没有自己的签发者。
2. 同一个外部系统（GitLab）有两个写者。预发布同步和正式同步都会按自己库里的成员建号，两者用的是两套 `sub`，GitLab 认不出是同一个人。
3. 迁移工具判断「这个人是不是成员」用的是已弃用的 `org_role` 字段，和 server 对外授权用的权限组不是同一个口径。

系统性原因：

- 预发布做过的事没有落到正式的账上（10-28 的三起都是这样），直到同构清单 `deploy/parity/ledger.json` 和 `parity` 门禁上线才有机器核对。
- 「一个外部系统只能有一个写者」没有写成检查。改接步骤要求先停旧写者，但正式写者可以在旧写者还开着时被打开。
- 改接是一串手工步骤，每一步的前置条件写在文档里，没有全部写进脚本。修复期间补上了：`repair-duplicates --apply` 在部署锁内核对正式写者已停，`switch-issuer` 要求预发布写者已停、主体全部迁完、49 名成员全部映射。
- GitLab 是比赛的唯一计分来源，出问题时没有备用的提交入口，也没有「先在 GitHub 提、恢复后迁回」的约定，参赛者只能自己想办法。

## 做得好的、做得不好的、运气

- 做得好：重复号只封不删，修复前跑一致性备份；每一步默认演算，任一条前置不满足整批拒绝；修复和迁移都能重跑接续。
- 做得不好：改接拖了两天，中间多次停下来问已经批准过的事；P0 窗口里混进了交互调整（代码仓库整页直达），hotfix 和普通改动没有分开。
- 运气：6 个重复号都没被登录过，所以能直接解绑封禁；6 人里除了维护者本人（在参赛名单上但不计分），没有参赛者。
