# LLM Wiki 搭建经验谈：别把知识库当垃圾场

> 整理自 2026-06-14 晚 i3eg1nner 的分享。他折腾了大半年 LLM 个人知识库，下面是去掉闲聊后的完整心得，方法论来自 Andrej Karpathy 的 LLM Wiki。

**要点速览**

- RAG 不是银弹，"全自动学习"是幻觉；知识库要**提前编译、持续维护**。
- **人选材料、问问题、做判断；LLM 干苦力**，这条分界线不能让。
- 三层目录 `raw/`、`wiki/`、`AGENTS.md`，从最小闭环起步。
- 四个日常操作：摄入、查询、健康检查、筛选入库。
- 工具没有最佳，只有最适合自己工作流的。

---

## 一、先泼冷水：RAG 不是银弹，全自动是幻觉

很多人一上来就想："把所有 PDF 扔进去，让 AI 自己学，不就完事了？"

并不能。

不加筛选地把几十篇没消化的论文丢给大模型，产出的东西根本不敢信。i3eg1nner 的比喻很直白：这叫**往知识库里倒垃圾**。信息不筛选、不消化、不整理，直接灌进去，知识库最后就是一个巨大的垃圾场。

Karpathy 提出的 LLM Wiki 方法论，核心只有一句话：

> **把"每次查询从零检索合成"改为"提前编译、持续维护"。**

传统 RAG 是每次提问临时从向量库里拼答案，没有积累。LLM Wiki 则让 AI 帮你把原始资料逐步"编译"成结构化的知识页面：知识在入库时就沉淀下来，而不是每次从零推导。

## 二、谁说了算？你，不是 AI

这是 i3eg1nner 反复摇摆后最终确定的底线：

**AI 负责所有苦力活：总结、归档、交叉引用、保持一致性。你负责选材料、问问题、做判断。**

具体来说：

- 让 LLM 先判断一份资料值不值得入库，但**最终决定权在你**。
- LLM 生成的总结，你要过一遍：删废话、补盲区、纠正概念偏差。
- 笔记比原文更有价值。经过你思考整理过的内容才是"知识"，原始 PDF 只是"原料"。

他见过有人想让 AI 全自动维护知识库，甚至幻想"自进化"。现实是：当前大模型上下文有限，自我学习能力不足，全自动的结果就是幻觉层层叠加，最后连哪句是真的都不知道。

这里有一个微妙的张力，i3eg1nner 自己也承认：他一边说"wiki 是为大模型服务的"，一边又强调"人类判断力是核心"。这两者其实不矛盾。wiki 的直接消费者是大模型（查询时喂给 LLM 当上下文），但**知识的生产和审核必须由人把控**。AI 是用 wiki 的人，不能让 AI 决定 wiki 里写什么。

## 三、怎么搭：三层结构，从简开始

别一上来就上复杂架构。最小闭环长这样：

```text
your-wiki/
├── raw/            # 原始资料，只读，不改
│   ├── articles/
│   ├── papers/
│   └── notes/
├── wiki/           # 编译后的知识，LLM 维护
│   ├── entities/   # 概念 / 实体页面
│   ├── concepts/   # 主题深度页面
│   └── summaries/  # 单篇摘要
├── index.md        # 知识索引
├── log.md          # 更新日志
└── AGENTS.md       # 告诉 LLM 怎么干活（Schema）
```

关键规则：

- **`raw/` 只读**：保留溯源能力，wiki 里的每个结论都必须能追溯到 `raw/`。
- **`wiki/` 完全由 LLM 写**：人不要手动改，改了也会被下次编译覆盖。想改内容，就改 `AGENTS.md` 里的规则，让 LLM 重新编译。
- **`AGENTS.md` 就是"行为契约"**：定义 LLM 怎么写、怎么链接、什么格式。改文档就等于改行为，不用写代码。

i3eg1nner 自己的实践是按领域划分子目录（AI 安全、硬件安全等），但他强调：分类体系不是一次定死的，而是在和大模型讨论中逐步迭代出来的，而且**经常需要手动调整**。这说明当前自动化方案的灵活性还不够，人的判断不可或缺。

## 四、四个日常操作

1. **Ingest（摄入）**：新资料到了，LLM 生成摘要，提取概念，建立双向链接，更新 `index` 和 `log`。
2. **Query（查询）**：先搜 wiki，wiki 没有的再去 `raw/` 找，LLM 综合回答；**好答案归档回 wiki**，这是复利增长的关键。
3. **Lint（健康检查）**：定期让 LLM 自查矛盾信息、过时内容、孤儿页面（没被任何页面链接）和断链。
4. **筛选入库**：不是什么都往里扔。i3eg1nner 举的极端例子是"牛板筋成分"这种琐碎信息，放进 wiki 就是污染。wiki 只保留核心概念实体，量少才能幻觉低。

## 五、工具选择：适配自己，别追全能

i3eg1nner 目前的方案是 **Mac mini + Obsidian + 坚果云**，每天人工判断增量内容是否值得入库。这个选择明显是为了对抗大模型"什么都想收录"的倾向。

他也调研过一个引入 MCP 概念的激进项目，核心结论是：**没有最佳方案，只有最适合你工作流的方案。** 有人用 Obsidian，有人用飞书，有人用 VS Code，强行统一工具链反而产生冗余操作。他举了论文管理工具整合的例子：跨平台协同的实际成本往往被低估。

轻量级个人 wiki，文档量在千级以下，配合 LLM 和人的判断力，就能搭出高效系统。Karpathy 推荐的 **Obsidian + Claude Code + Git + Markdown** 是目前最稳健的入门路径。

## 六、写在最后

知识管理的核心不是你存了多少，而是你能用多少。

i3eg1nner 有几句话值得反复琢磨：

- 别追求完美工具：完美主义是效率杀手。
- 别幻想全自动：大模型当前做不到自进化，硬做只会搞出一堆幻觉。
- 别什么都往里塞：输入质量决定输出价值，垃圾进垃圾出。
- 笔记比原文珍贵：经过思考整理的内容才有深度，原始资料只是原料。

**人类选材料、问问题、做判断；LLM 干苦力。这条分界线守住了，知识库才会越用越聪明。**
