## 1. Vibe Coding 是什么

- Vibe Coding 指**用自然语言向 AI 描述想法，让 AI（Agent）帮你写代码、跑命令、改 bug** 的开发方式。
- 核心理念：**AI 是"副驾驶"，方向盘必须在自己手里**。AI 可以帮你提速，但理解、判断与责任都属于你。
- 它不是"一句许愿就完事"，而是一套有方法的工作流：**先读项目地图 → 多轮对话把需求聊成 spec → 小步迭代 → 逐 diff review**（详见第 5 节）。
- 这套做法能成立的底层逻辑：大模型在语义理解上足够强（语言成了通用接口），配合工具与循环就成了能独立干活的 Agent；Coding Agent 就是把这一套落到编程场景的产品形态。

### 1.1 判断力（Developer Taste）：Vibe Coding 的质量闸门

AI 能生成代码，但"什么是好代码"的判断力只能长在人身上：

| 维度   | 含义                                                         |
| ------ | ------------------------------------------------------------ |
| 简洁   | 每行代码都有存在的理由；能 5 行说清的事，不用 20 行；警惕"过度防御" |
| 高效   | 选对数据结构与工具，不为不存在的需求提前优化，也不容忍明显浪费 |
| 可读   | 命名说人话、结构一眼到底；代码被阅读的次数远多于被编写的次数 |
| 可维护 | 改动有边界、依赖讲清楚、测试能兜底                           |

Taste 的养成没有捷径：**大量阅读好代码 + 亲手 review 每一处 AI 的产出**。每次 review 都问一句："这样写，够简洁、够清楚吗？"

另一个实践原则是"落笔之前先在脑海里把项目建一遍"：动手前想清楚整个项目分几层、每层用什么技术、坑会出在哪里（例如网站服务 = 前端 + 后端逻辑 + 数据库三层解耦），需求才写得准，验收点才定得明。反例是放任 Agent 自由发挥，把整个网站写成单个 `index.html`：能跑，但改一处动全身，可维护性约等于 0。

## 2. 大模型基础

> 核心：**大模型不会"思考"，它是一个超强的"下一个词预测器"**。理解这一点，才能理解它为什么强、为什么会一本正经地胡说八道。

**全链路总览**：文字 → Token → 向量（Embedding）→ Transformer → 概率 → 采样 → 再循环。"思考"本质就是这台预测机器反复运转。

### 2.1 Token：把文字切成最小单位

- 模型不认识"字"和"词"，只认识数字。**Token 是文本被切碎后的最小单位**，每个 token 对应一个编号（分词过程叫 tokenize）。
- 一个单词可能被拆成多个 token，例如英文 `unbelievable` → `un believ able`。
- **要记住的三件事**：Token 是**计费单位**（API 按 token 收费）；**上下文窗口以 token 计**（不是字数）；切词方式解释了模型的某些"怪癖"（如数字、字母、拼写出错）。

### 2.2 Embedding：Token → 向量

每个 token 被映射成一串数字（向量），**语义越相近，向量在空间里的位置越靠近**。

![Embedding 示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082237704.png)

- 示例：猫 → [0.21, -0.58, 0.83, …]；狗 → [0.19, -0.61, 0.79, …]；编译器 → [-0.72, 0.34, 0.11, …]。"猫"和"狗"的向量很接近，"编译器"离它们很远。
- 经典运算：**国王 − 男人 + 女人 ≈ 女王**。把「国王 − 男人」得到的"王室"方向加到「女人」上，落点正好是「女王」。
- 意义：向量把语义变成可计算的距离（意思变坐标、关系变方向），模型才能在连续的语义空间里做计算，而不是死记硬背。

### 2.3 Transformer：算下一个 token 的概率

向量序列进入一个叫 Transformer 的神经网络。**它只做一件事：算出下一个 token 的概率分布**。

![Transformer 示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082315546.png)

- 图左列是全链路回放：Token 序列 → Embedding 向量 → Transformer → 下一个 token 的概率（如 线上 42% · 晚上 25% · 今天 15% …）。
- 图右是 Transformer 块内部（GPT 式简化）：**Self-Attention** 让 token 之间交换信息，**前馈网络 FFN** 在每个位置独立计算；每个向量还会加上**位置信息**，模型由此知道词的先后顺序。
- 同一个 Transformer 块叠 N 层（几十到上百层）。GPT 的「T」就是 Transformer。

### 2.4 核心机制：预测下一个 Token + 采样

大模型做的唯一一件事：给定上文，计算所有候选下一个 token 的概率分布，然后**采样**一个，再拼回上文继续。

![采样示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082344134.png)

- Transformer 最后一层给**词表中每一个** token 算出"出现在下一个位置"的概率，全部加起来正好 100%，再按概率抽一个。
- 词表 = 模型的"全部词汇"，主流模型约 5 万到 15 万个 token，每一个都会分到一点概率（趋近于 0，但都不是 0）。
- 大模型 = 一个读过整个互联网的"接龙高手"：它生成的是**最像答案的文本，而不一定是正确答案**。
- 两个重要推论：
  - **抽样 ≠ 总选最大的**：同一个问题问两次，回答会不一样（可复现性天然差）。
  - **温度（temperature）**：调低更保守（只挑大概率），调高更随机。
- 训练 = 在海量文本上玩亿万次"接龙"，不断调整参数让正确接法概率更高；模型学到的是语言的统计规律以及其中蕴含的知识与模式，**没有任何一步在"查证事实"**。像真的，不等于真的。

### 2.5 Self-Attention：模型怎么"看"上下文

每个 token 都拿着自己的 **Query**，去和（自己及之前的）每个 token 的 **Key** 算一次匹配分。分越高，"看"得越仔细。

![Self-Attention 示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082359667.png)

- 比喻：Key 行是每个 token 亮出"名片"，Query 行是每个 token 发起"提问"。
- 关键规则：**每个 Query 只与"自己及之前"的 Key 计算（不偷看未来）**；线越粗 = 匹配分越高。
- 示例：在「小猫 追 毛线球 ， 因为 它 饿了」中，以「它」为 Query 时匹配分主要落在「小猫」上，模型由此"知道"它指代谁。
- 意义：Self-Attention 让模型根据上下文**动态聚焦相关信息**。**上下文给得越准，它"看"得越准，这是写好 prompt 的第一性原理。**

### 2.6 上下文：模型唯一的"工作台"

注意力只能分配在**上下文窗口**里：你没给的信息它看不见，你硬塞的信息它甩不掉。

- 窗口内（模型看得见）：你的问题、你贴的代码、完整报错日志、环境与版本。
- 窗口外（模型完全看不见）：没贴的项目文件、你的电脑环境、昨天试过的方案。
- 没有"心灵感应"：窗口外的一切它只能靠脑补，这是**幻觉的根因之一**。

**三条推论**：管好上下文是用好 AI 的第一步；窗口有限，塞入无关内容会稀释注意力、淹没关键信息；所以是**"给准"不是"给多"**（相关代码、完整报错、环境版本）。

### 2.7 两步修炼：从"接龙高手"到"编程助手"

同一个模型，先靠**预训练**"学知识"，再靠**后训练**"学做事"。

![预训练与后训练示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082419801.png)

1. **预训练（Pre-training）**：在海量文本上玩亿万次接龙，学会语言与世界知识。产物：只会续写的 Base Model。
2. **后训练（Post-training）**：把"接龙高手"调教成"助手"的三道工序：
   - **SFT（监督微调）**：用"指令 - 回答"对训练，学会听懂任务、按要求作答；
   - **RL（强化学习，如 RLHF）**：人或规则给回答打分，学着往高分靠，更好、更安全、更会推理；
   - **Distill（蒸馏）**：用另一个模型的输出当教材来训练，低成本复制能力，老师不一定是强模型。

> 预训练决定它"知道多少"，后训练决定它"多好用"。后训练给的三种能力：按对话格式输出、编写代码、**使用工具**。其中"使用工具"打开了 Agent 的大门。

### 2.8 幻觉：为什么会一本正经地胡说八道

两个根因，都来自"它是概率生成器"这一本质：

- **根因一：概率生成 ≠ 事实证明**。模型输出的是"最像答案的文本"，训练数据里模糊的、过时的、少数派的知识，都可能被它理直气壮地说出来。
- **根因二：上下文不完整 → 自动"补空白"**。你没给的代码、没说的约束，它不会问，而是编一个最合理的填上。这正是"幻觉 API"的来源。

**编程里的典型幻觉**：

- 编造不存在的函数 / 参数 / 包名（"看起来就应该有"）；
- 引用过时的 API（训练数据停留在旧版本）；
- 声称"已修复"，实际改动没有生效；
- 对你没给的文件，脑补出一份"合理"的内容。

> 应对幻觉没有银弹，只有闭环：**工具验证（编译、测试、运行）+ 人工 review**。永远不要让 AI 的输出绕过你的检查直接进入代码库。

### 2.9 小结：能力与边界

| 强在哪里 ✓                               | 边界在哪里 ✗                           |
| ---------------------------------------- | -------------------------------------- |
| 模式：见过海量代码套路，样板代码信手拈来 | 不保证事实正确（幻觉）                 |
| 语义：能读自然语言需求，也能解释代码意图 | 不真正运行代码，除非接上工具           |
| 生成：速度快、不知疲倦、风格统一         | 不知道你的项目全貌，除非你把上下文给它 |

**正确闭环**：AI 生成（草稿 / 建议 / 改动）→ 工具验证（编译 · 测试 · 运行）→ 人工 Review（读懂 · 判断 · 负责）。

## 3. Agent 原理

> 核心：**Chat 是"你问我答"；Agent 是"给我一个目标，我自己看、自己想、自己动手、自己检查"**。区别就在于那个循环。

### 3.1 从 Chat 到 Agent：多了"一个循环"

![Agent 循环示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082436622.png)

- **普通 Chat**：你提问 → 模型生成回答 → 结束。模型没有"手"：不能看你的文件、不能跑命令，你得手动复制粘贴代码和报错，当"人肉中间件"。
- **Agent**：目标驱动、循环执行：① Observe 观察 → ② Think 规划 → ③ Act 行动 → ④ Check 检查 → ⑤ Iterate 迭代 → 直到任务完成或达到上限。

> **Agent = 大模型 + 工具 + 循环**。模型负责决策，工具负责动手，循环负责"做到底"。

### 3.2 ReAct：边推理，边行动

Agent 的经典工作方式：**Reasoning（想）与 Acting（做）交替进行**，每一步都想清楚再做、做完再看。三要素：

- **Thought**：模型用自然语言写下当前判断和下一步打算；
- **Act**：调用一个工具，做一件具体的小事；
- **Observe**：把工具结果喂回模型，进入下一轮。

完整示例，任务：修复登录页按钮点击无反应的问题：

```text
Thought：先看登录页代码在哪
Act    ：read_file("src/pages/Login.tsx")
Observe：按钮 onClick 绑定了 handleSubmit
Thought：怀疑 handleSubmit 里提前 return
Act    ：read_file("src/hooks/useAuth.ts")
Observe：第 42 行 token 为空时直接 return
Thought：找到原因了，改成弹提示而不是静默返回
Act    ：edit_file("src/hooks/useAuth.ts", …)
Observe：修改成功
Thought：验证一下
Act    ：run_command("npm test")
Observe：14 passed ✓
```

> 这个轨迹（trace）通常对你可见：你能看到它每一步在想什么、做了什么，这正是你 review 的依据。ReAct 的好处：**决策过程透明、可检查、可打断**，看到它想歪了随时纠正。

### 3.3 工具调用：模型怎么"动手"

模型本身不会执行任何操作。**它只是输出一段结构化的"调用请求"，由外部程序真正执行，再把结果喂回来**。

```json
{
  "tool": "run_command",
  "arguments": {
    "command": "npm test",
    "timeout": 120
  }
}
```

工具调用三步：① 选工具（从可用工具列表里挑一个）→ ② 填参数（按 schema 输出 JSON）→ ③ 读结果（观察 observation，继续决策）。

关键点：

- 每个工具都有"说明书"（**schema**）：名字、用途、参数类型；
- 模型的输出被程序解析并真正执行：读文件、改代码、跑命令、查网页；
- 执行结果作为新上下文回到模型，这就是一轮 **tool calling**；
- 参数填错、文件路径写错并不少见，所以工具层要做**校验和权限控制**，不能模型说跑啥就跑啥。

> 一句话：**模型是"发指令的人"，工具层是"干活的"**。手的权限必须被约束。

### 3.4 MCP：Agent 的"万能转接头"

**Model Context Protocol**：一套开放协议，让 Agent 用统一方式接入外部数据、工具和 prompt 模板。

![MCP 示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082453024.png)

- MCP 能提供三类东西：**工具**（可执行的操作）、**资源**（可读取的数据）、**prompt 模板**（预置的任务说明）。
- 价值对比：
  - 没有 MCP：每接一个新系统都要定制开发，N 个 Agent × M 个系统 = 灾难；
  - 有了 MCP：系统实现一次 MCP server，所有支持 MCP 的 Agent 都能用。

### 3.5 Skill：给 Agent 装"技能包"

不训练模型、不改代码，**把"怎么做某类事"的经验打包成说明书**，Agent 发现任务匹配时自己翻开照做。

```text
skills/pdf-report/
├── SKILL.md       ← 说明书：什么时候用、分几步做、注意什么
├── scripts/       ← 可复用的脚本（Agent 可以拿去跑）
└── templates/     ← 模板与参考文件
```

- Skill = 一份"做事说明书"（SKILL.md）+ 配套资源，打包成一个文件夹。
- 工作流程：① 发现（任务匹配 skill 描述）→ ② 加载（把 SKILL.md 读进上下文）→ ③ 照做（按说明书组合使用工具）。
- **按需加载**：只有任务匹配时才读进来，平时几乎不占上下文。
- 和工具互补：工具回答"能做什么"，Skill 回答"**该怎么做**"：流程、规范、窍门。
- 你可以自己写：把项目约定、部署流程打包成 skill，Agent 每次都照同一套 SOP 做。

> MCP 把外部世界接进来，Skill 把经验装进去，两者都让 Agent 从"通用"变"懂行"。工具给了 Agent"手"，Skill 给了它"手艺"。

### 3.6 权限与沙盒：能力越大，边界越要清楚

| 能力         | 典型风险                       | 常见防护                               |
| ------------ | ------------------------------ | -------------------------------------- |
| 读文件       | 看到密钥、隐私数据并带入上下文 | 限制工作目录；敏感文件默认禁读         |
| 改代码       | 误改、大改、改坏               | 改动以 diff 呈现，确认后落盘；Git 兜底 |
| 跑命令       | rm -rf、装恶意依赖、泄露数据   | 逐条确认 / 白名单；沙盒内执行          |
| 访问外部系统 | 误发消息、误操作线上资源       | 最小权限 token；写操作需人工批准       |

- **沙盒（sandbox）**：给 Agent 圈一块"隔离场地"，只能动这个目录、只能连这些地址、命令在受控环境执行。就算它想歪了，破坏也出不了圈。
- **原则：最小权限 + 关键操作人工确认**。方便可以慢慢放开，事故一次就够：
  - 不要随手给 Agent"全部允许"的免确认模式；
  - 密钥、证书永远不要出现在它能读到的位置；
  - 重要操作前先看 diff / 命令内容，再点确认。

### 3.7 语义即智能：语言是通用接口

为什么偏偏是语言模型能驱动 Agent？因为相当大一部分任务都能用语言描述，而语言模型天生就理解和操控语言：

| 任务环节 | 对应的"文本"               |
| -------- | -------------------------- |
| 需求     | 自然语言                   |
| 代码     | 编程语言（也是文本）       |
| 文档     | Markdown / 注释            |
| 报错     | 日志与堆栈文本             |
| 接口     | JSON / Schema / 协议文本   |
| 工具调用 | 一段结构化的"调用请求"文本 |

全部是文本，全在语言模型的射程之内。

- 模型读懂语义 = 通用接口：**自然语言就是 API**，不必为每个任务写专用解析层；
- 工具调用的本质也是文本：模型写一句 JSON，宿主程序解析执行，**说即是做**；
- 这就是 Agent 近两年爆发的原因：语义理解一旦够用，语言立刻变成"万能遥控器"；
- 但边界也在这里：**能描述 ≠ 能做对**，所以才有权限与沙盒。

## 4. 常见 Coding Agent

> 不做排名、不追新潮。按"任务发生在哪里"分类，理解各自的适用场景，然后学会怎么选。

### 4.1 四类工具：按"上下文在哪"分类

| 类别                | 特点                                                         | 适合                                                |
| ------------------- | ------------------------------------------------------------ | --------------------------------------------------- |
| ① IDE 内联助手      | 住在你光标里：代码补全、局部解释、局部重写。你看它写，随时敲键盘纠正 | 写函数片段、补边界处理、解释眼前这段代码            |
| ② IDE Agent         | 住在编辑器里的 Agent：跨文件修改、自己跑命令、改动以 diff 呈现等你确认 | 中小功能开发、重构、修 bug，你想全程盯着            |
| ③ 终端 Agent（CLI） | 住在终端里：面向整个 repo，擅长脚本化、批量操作、和命令行工具链配合 | repo 级任务、批量迁移、调试、写脚本、自动化         |
| ④ 云端 Agent        | 住在云端：认领 issue / 任务后独立工作，产出 PR 等你 review，异步进行 | issue / PR / backlog 级任务，边界清晰、验收标准明确 |

**从上到下：自主性越来越强，你"盯"的能力越来越弱。越靠后，任务描述和验收标准越要写清楚。**

新手建议以 ①②（IDE 内联与 IDE Agent）为主战场：改动看得见、学得着、拦得住，每个 diff 都是一次免费的教学。

### 4.2 怎么选：四个问题

选择口诀：**上下文决定形态，风险决定权限，验收决定放手程度，责任永远在己。**

1. **上下文在哪里？** 任务只涉及眼前几行 → 内联；跨文件 → IDE Agent；整个 repo / 要跑脚本 → 终端 Agent；能被一个 issue 完整描述 → 云端。
2. **风险有多大？** 会碰数据、密钥、线上服务、删文件？→ 选你能逐步确认的形态，并收紧权限。
3. **如何验收？** 有测试、能运行、能看效果 → 才值得交给自主性高的形态；验收说不清 → 先自己做或拆小。
4. **谁来负责？** 永远是你。所以选让你看得懂、拦得住的工具与粒度。

| 形态       | 协作模式 | 风险 |
| ---------- | -------- | ---- |
| 内联       | 你写它补 | ≈ 0  |
| IDE Agent  | 它改你审 | 低   |
| 终端 Agent | 它跑你盯 | 中   |
| 云端 Agent | 它做你验 | 高   |

### 4.3 代表产品与模型速览（口径 2026-07-24，功能以官方文档为准，排名不分先后）

| 产品               | 形态                    | 一句话认识                                                   |

## 5. 实战工作流：把 Vibe Coding 用对

> 同样的工具，有人用出 10 倍效率，有人制造 10 倍混乱。差别全在工作流。

### 5.1 第 0 步：先让 AI 帮你读"项目地图"

不要一上来就让 AI 写功能。**顺序铁律：先理解，后生成**。看不懂的项目，AI 写得越快，你欠的债越多。

面对一个新项目，先问 Agent：

> "请通读这个仓库，然后告诉我：
>
> 1. 项目的整体结构和每个目录的职责
> 2. 程序入口在哪，主要数据流怎么走
> 3. 核心模块是哪几个，它们怎么交互
> 4. 如果我以后要加 X 功能，最可能要动哪些文件？"

- 让 Agent 讲给你听，而不是替你记住；
- 对照它的讲解，亲自打开关键文件读一遍；
- 有了地图，后面每个改动你都知道动的是哪根神经。

### 5.2 别憋"完美 prompt"：和模型多轮聊出需求

现在模型已经会主动提出合理的问题，需求澄清可以放心交给对话。聊完对照"及格线"四要素：

- **Goal 目标** · **Context 上下文** · **Constraints 约束** · **Done when 验收**

四要素齐了，才算需求聊清了。四要素不是"写作模板"，而是需求收敛后的验收清单。

对话四步：① 说个大概（一句话说清想要什么，不用完美）→ ② 让它追问（明确要求它先提问、先给方案，别急着写码）→ ③ 你答你改（回答它的问题，纠正它的假设）→ ④ 收敛成 spec（让它把结论整理成任务书，你确认后才动手）。

**反向操作：让 Agent 先"采访"你**。需求说不清是常态，与其硬写 spec，不如让 AI 帮你把需求问清楚：

> "我想给项目加一个排行榜功能。在动手之前，请先采访我：逐个问我你需要明确的问题（数据、交互、样式、边界情况），每次最多问 3 个；等我回答完，把结论整理成一份任务 spec 让我确认，确认后再开始写代码。"

- 进阶：让 Agent 在 spec 里标注"我假设了……"，把它的脑补摊在阳光下，你逐条确认或纠正。
- 很多 Agent 自带 **plan mode**：先探索项目、给出实施方案，你批准后才写码，相当于把"采访 + 确认"做成了内置流程。
- **好用** = 多轮对话收敛需求，坏用 = 一句话许愿。AI 不怕你问得多，就怕你说得少。

一个完整示例（对话是过程，spec 是产物）：

> 你：我想给项目加一个排行榜功能。
> Agent：动手前确认几点：① 数据从哪来，现有接口吗？② 展示多少名？前三名要特殊样式吗？
> 你：用 `src/api/score.ts` 的 `getTopUsers()`；前 20 名，前三名要有视觉区分。
> Agent：边界再确认：能引新依赖吗？样式沿用现有方案？
> 你：不引新依赖，风格参考现有页面。
> Agent：明白。整理成 spec：Goal：积分排行榜页，展示前 20 名；Done when：build 通过；mock 可渲染；前三名有视觉区分。确认无误的话，我开始写。

### 5.3 小步迭代：AI 时代的开发节奏

这就是"生成 → 验证 → review"闭环的实战形态。**循环越快，风险越小，学得越多。**

![小步迭代示意](https://gitee.com/defensive-leader/picgo-bed/raw/master/20260909082514923.png)

1. **读结构**：让 AI 讲解相关代码，自己也读一遍；
2. **小改动**：一次只做一件事，拒绝"顺便重构"；
3. **跑测试**：编译 / 测试 / 运行，让工具说话；
4. **Review**：diff 逐行看懂再接受，不懂就追问；
5. **总结提交**：归纳改动要点，Git 小步提交。

- 每步都可回滚：**Git 是你的安全气囊，小步提交 = 频繁存档**。一步出错只退一格，一口气生成 500 行，出错就是灾难现场。
- 第 ④ 步不是形式：**看不懂的代码不许入库**。
- 每圈迭代结束让 AI 总结改动，对照你的理解，不一致就查。
